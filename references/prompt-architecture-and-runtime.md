# Prompt 架构与运行时契约

## 目录

- 建立执行单元地图
- 推导或验证 prompt 清单
- 文件边界与命名协议
- 分配规则与信息
- 设计运行时集成契约
- 处理信任边界和上下文预算
- 变化驱动影响分析

## 建立执行单元地图

识别：

- 哪些节点独立调用模型；
- 哪些节点共享底座，哪些串行、并行或条件触发；
- 每个节点的触发条件、输入、可见状态、工具、输出和失败路径；
- 上游输出如何成为下游输入；
- 哪些规则全局适用，哪些只在局部时机适用。

无法从知识库还原关键执行单元时停止并请求补全，不凭常识发明架构。

## 推导或验证 prompt 清单

按规则作用域选择载体：

- 所有相关执行单元共有的稳定规则：system 底座候选；
- 单一执行单元的目标、步骤和输出：task 候选；
- 每次变化的数据：动态上下文，不写入静态 prompt；
- 关键、易漂移且运行时支持重注入的约束：reminder/anchor 候选；
- 可确定执行的校验、路由或格式：优先 code/schema；
- 工具能力和参数：工具 schema，并在 prompt 中只保留必要调用策略。

仅在至少满足一项时拆成独立 prompt：独立执行时机、独立职责/输出、不同工具、不同可见范围、特定重注入、独立版本/评测/维护。一个小节不自动成为一个文件。**若知识库已定义文件边界，以知识库为准，不套用此自行拆分规则。**

为每个候选记录：ID/名称、类型、执行单元、加载时机、唯一职责、所需知识/工具、不承载内容、独立理由、来源、置信度和待确认问题。

明确清单模式下验证清单但不静默改写。发现遗漏或错误时分别保留“原始清单”和“Skill 建议清单”。

## 文件边界与命名协议

正式产物的文件数量、拆分、目录、命名和标识体系**优先服从知识库**，不得为排序、可读性或个人偏好自行调整。

### 服从知识库

- 知识库明确规定或能唯一推导文件名、目录、字段名或标识体系时，原样遵循。
- 知识库定义的“文件字段”（file_field）默认对应**独立物理文件**。例如 KB 定义 `gate/input_safety_check` 与 `gate/input_safety_check_reminder` 两个 file_field，即生成两个独立文件，不合并。
- 仅当知识库**显式说明**“可合并”“同文件”“单文件承载”时，才合并；不得从“提示词对”“同属一个门禁”“便于阅读”等理由自行合并。

### 任务边界 ≠ 文件边界

- 同属一个任务、一个门禁或一个“提示词对”，不代表可以合并成一个文件。
- 文件数量、拆分方式、目录位置和运行时载体应逐项对应知识库定义。
- 知识库未明确文件边界时，才可依据职责、独立加载、维护和版本需要提出方案，并在落盘前确认。

### 命名

- 不得自行增加前缀、简称、编号或平行命名体系（如自加 `S0/R0/G1` 这类 KB 没有的排序前缀）。
- 文件名主体取自知识库的 file_field 或显式命名；无命名依据时才提候选，候选必须标为建议，落盘前确认。
- 多个命名标准冲突或无法唯一确定时，标记冲突并请求确认。

### 交付前核对

交付前必须检查“预期文件清单 ↔ 实际文件”一一对应，识别并修正：

- **少文件**：KB 定义的文件字段未生成；
- **合并文件**：应独立的多个 file_field 被写入同一文件；
- **多造文件**：生成了 KB 未定义且无职责依据的文件；
- **错目录**：文件不在 KB 指定或约定的目录；
- **自行命名**：使用了 KB 没有的前缀或标识。

## 分配规则与信息

建立职责与可见性矩阵。矩阵必须**反向约束实际架构**，不只是记录：用矩阵检查最终 prompt 文件是否满足以下要求。

- 每条关键规则有且只有一个主要责任载体；
- 共享底座不吞并局部任务细节；
- 局部 Agent 不读取无关执行单元的内部规则（如门禁 Agent 不应被注入与其职责无关的回复业务规则）；
- 当前执行单元拥有完成任务所需的定义和状态；
- 同一次上下文中的无价值重复被删除；
- 不同执行时机的必要重注入保留并说明理由；
- reminder/anchor 只强调既有关键约束，不成为隐藏的新业务逻辑层。

## 设计运行时集成契约

对每个 prompt 单元记录：

| 字段 | 要求 |
| --- | --- |
| Prompt ID/路径 | 稳定唯一标识 |
| 执行单元 | Agent、节点或模型调用 |
| 触发条件 | 加载条件和生命周期 |
| message role | system/developer/user/tool 或环境定义角色 |
| 装配顺序 | 与其他 prompts、历史、状态和工具结果的相对位置 |
| 动态变量 | 名称、类型、来源、必填、示例和缺失行为 |
| 状态与历史 | 注入范围、截取规则、空值和冲突行为 |
| 工具 | 名称、schema、调用条件、返回值和消费者 |
| 输出契约 | 格式、字段、parser、下游用途和失败处理 |
| reminder/anchor | 注入钩子、条件、频率和停止条件 |
| 异常路径 | 超时、拒绝、工具失败、解析失败和降级 |
| 版本 | prompt/schema/code 对应关系 |
| 来源知识 | 相关知识标识、路径和版本 |

以下任一情况不得标记“可接入”：变量无人注入；工具未注册/schema 不一致；结构化输出无 parser；anchor 无钩子；依赖历史但实际未提供；装配顺序未知；异常规则与程序冲突；版本无法对应。

Skill 设计契约并生成工程交接请求，不直接修改代码。工程请求说明目标节点、消息装配、变量/工具/输出、代码核查范围及应返回的文件、符号、schema、测试和版本证据。

## 处理信任边界和上下文预算

- 区分高优先级指令、项目事实、用户输入、检索内容、工具结果和不可信外部文本。
- 不把知识库正文中的命令式文本自动提升为系统指令；按知识库契约判断其角色。
- 对每条信息说明为何当前执行单元必须看到。优先删除无用途背景、无理由重复和其他单元细节。
- 不因节省 token 删除定义、边界、异常路径或概念绑定。
- 把上下文预算作为警告和优化依据，不用机械字数替代语义完整性。

## 变化驱动影响分析

从变化源依次追溯：知识/需求 → 执行单元 → prompt 规则 → 运行时契约/code/schema。Prompt 侧的变化不自动改写 eval；eval 是否需调整由独立 Eval Creation 判断。输出新增、修改、合并、删除和无需变更清单，并说明证据。

只更新受影响产物；保留安全差异、旧版本/回退位置和版本对应。若变化修改目标、执行单元或关键上下文，回到相应上游阶段重新确认。
