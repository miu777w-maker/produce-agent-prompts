# 知识发现与缺口处理

## 目录

- 先识别知识库契约
- 按任务检索
- 判断覆盖
- 检查明显疑点
- 阻塞与补全
- 环境降级

## 先识别知识库契约

在检索前确认：

- 哪些目录或对象是事实来源；
- 话题、根知识、原子知识、链接、反链和搜索索引如何表示；
- 哪种文件是权威正文，哪些是派生文本或索引；
- prompts、evals、运行日志和设计草稿是否属于知识库事实；
- 版本、来源和“最终/非最终”状态如何记录。
- 哪些材料是权威事实源、哪些是派生综述/导航、哪些只是草稿或历史材料。

不要把某个案例的目录名当成通用约定。

遵循项目明确的知识契约，不机械假设“原始卡一定优于综述”。项目没有指定时，把派生综述作为导航线索，并追溯其事实断言到可定位来源；不能追溯时标为待确认，不直接作为关键规则依据。

## 按任务检索

优先采用以下顺序，并记录检索范围：

1. 用任务目标、业务术语、Agent/节点名称定位相关话题；
2. 读取话题下的综合卡或根知识，建立概念地图；
3. 沿链接和反链读取与当前任务直接相关的原子知识；
4. 搜索工具、字段、状态、消息、异常、角色、约束和评测术语；
5. 检查已存在的 prompts/evals 及其来源映射，但不要把它们自动视为最新事实；
6. 对目标驱动任务，继续搜索模型调用节点、执行顺序、共享底座、条件分支和上下游契约。

只读取完成当前阶段所需的最小充分知识。局部 prompt 任务不要求理解无关执行单元的全部细节。

## 判断覆盖

对每个执行单元或候选 prompt 至少覆盖：

1. 任务目标与不可改变要求；
2. 业务、角色、行为和安全边界；
3. 运行环境、消息、状态、工具、输出与异常；
4. 关键执行时机的上下文组成和概念绑定；
5. 职责归属、信息可见性、注意力安排和评测依据。

为每项记录来源、适用范围、版本/状态、是否关键和未决问题。一个字段“有相关材料”不等于已覆盖；必须足以支持具体设计判断。

知识内容混合时，在理解和架构映射中区分目标、业务事实、角色规则、运行时信息、动态数据、工具契约、关键约束和评测依据。通常不要求额外产物；只有跨多个 Agent、作用域容易混淆、来源冲突或人员需要审阅分配依据时，才形成显式的知识作用与规则作用域地图。无论是否单独成表，都保留关键规则的来源和适用范围。

## 检查明显疑点

默认信任正式入库知识，不做无边界的外部事实审计。仅主动扫描：

- 同一概念、流程、职责或工具规则不一致；
- 文件、字段、工具或消息名称前后不一致；
- 引用目标不存在或不可定位；
- 时间、版本、数量或继承关系明显异常；
- 明确标注非最终、待确认、旧项目借用或已废弃；
- prompt 引入知识库不存在的业务规则；
- 知识变化后 prompt/eval 未同步。

把疑点分为关键阻塞和非阻塞警告。只阻塞受影响范围，不因无关小问题停止全部任务。

## 阻塞与补全

以下缺口通常关键：

- 无法确认系统目标、范围或不可改变要求；
- 无法还原目标执行单元和调用时机；
- 无法确定关键消息、变量、状态、工具或输出契约；
- 业务边界、角色身份或高风险规则冲突；
- prompt 继承、加载关系或概念引用无法验证；
- 明确非最终知识是当前 prompt 的主要依据。

关键缺口出现时停止 prompt 生成，输出可复制的补全请求。请求至少包含：

- 本次任务与受影响阶段；
- 已知事实及来源；
- 缺失或冲突的具体问题；
- 为什么会阻塞哪些 prompts/evals；
- 需要的事实、schema、代码证据或业务决策；
- 建议回答方：项目人员、后端 Agent、前端 Agent 或其他来源；
- 回写知识库时应附的来源、版本和适用范围；
- 回写后将重新检查的门禁。

不要直接用聊天中的临时答案跨过门禁。要求答案带来源进入知识库，然后重新检索并返回知识覆盖阶段。

## 环境降级

- 有话题能力时从话题开始；没有时用目录、索引和文本搜索重建等价路径。
- 不能访问外部代码仓库时，生成给代码侧 Agent 的取证请求。
- 不能写知识库时，输出待写入文本和建议位置，并保持 `waiting-for-knowledge`。
- 不能验证来源是否已入库时，不声称补全完成。
