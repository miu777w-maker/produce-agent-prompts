## 四、第五 Skill `runtime-integration-validation` 评估

### 必要性

**建议独立成第五 skill**(本轮不新建)。理由:

1. **访问边界不同**:它是唯一默认需要后端仓库授权的 task skill;其他四个默认 KB-only。把后端取证塞进 Inspection 会破坏 Inspection 的"KB 视角"边界,且违反"Inspection 默认不访问外部仓库"。
2. **方法不同**:Creation=生产;Inspection=应有体系 vs 现有文件(KB 视角);Revision=改写;Eval Creation=评行为;**runtime-validation=元信息预期 vs 后端代码事实对照(实际视角)**。对照型工作流独立于生产/检验/改写/评测。
3. **是 §四"两环境分离"的执行臂**:KB 环境(Creation/Inspection/Revision)与后端环境(runtime-validation)的分离,天然对应 skill 分离。
4. **已实证**:第二轮修订报告(`Prompt修订报告_第二轮.md`)本质就是这个工作流——3 个 Explore 代理后端取证、对照元信息、归因四类(Prompt 误写/KB 过时/后端偏差/无法判断)、产出工程修改请求 + KB 补充请求。它独立存在且有价值。
5. **渐进披露友好**:仅在"后端校验"阶段经用户授权启用,其他阶段不加载。

### 职责边界(草案)

- **输入**:带元信息的 Prompt 生产稿 + 用户明确授权的后端仓库地址 + 授权检查范围 + KB/Prompt 生产依据。
- **检查**:Prompt 文件被代码如何读取;system/task/reminder/anchor 真实装配顺序;每 Agent 实收消息;动态状态注入;工具名/参数/枚举/返回结构;输出消费;拒绝与异常路径;文件名 vs 代码配置;组合后跨层冲突。
- **输出**:元信息预期 vs 代码事实对照表;Prompt 问题;后端实现问题;KB 过时问题;无法判断项;上线阻断项;KB 补充请求;工程修改请求。
- **约束**:默认只读后端、只报告;不改 Prompt/KB/代码;差异归因不静默选边(回归 17);Prompt 问题转 Prompt Revision、KB 过时转人员补 KB、后端偏差转工程请求;元信息在此阶段保留(对照依据)。

### 复杂度对比

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **独立第五 skill**(推荐) | 职责/访问边界/方法清晰;不污染 Inspection 的 KB 视角;是两环境分离的执行臂 | skill 数 4→5;需定义其七项映射(对照后端版)与触发 |
| 作为 Inspection 的运行时模式 | 不增 skill 数 | Inspection 要分裂"KB 视角/后端视角"两模式,边界模糊;且 Inspection 默认不访问后端,需加例外,破坏 §三 外部边界规则 |

**结论**:独立成第五 skill 更干净;但**本轮不新建**,待审查批准 + 回归设计后,在正式迁移时纳入。
