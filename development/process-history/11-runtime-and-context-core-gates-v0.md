# 原始输入核心门禁：运行环境与执行时机上下文 V0

> 目的：把原始输入前两条从分散检查提升为正式 Skill 中不可跳过的核心产物与门禁。

## 一、核心门禁 A：Agent 运行环境说明

对本次任务涉及的每个 Agent、任务节点或独立模型调用，Skill 必须获取并记录：

### 身份与执行位置

- Agent / 节点名称；
- 在系统中的位置；
- 触发条件；
- 上游与下游；
- 是独立 Agent、共享 MainAgent 上的任务，还是普通模型调用。

### 模型可见输入

- system message；
- task/developer 类消息；
- reminder/anchor；
- 用户消息及其包裹方式；
- 对话历史；
- memory、事件状态、页面状态或其他动态数据；
- 工具描述与 schema；
- 检索知识或外部结果（如存在）。

### 工具与能力

- 可见工具名称；
- 每个工具的用途、参数、返回结构和错误；
- 必须调用、条件调用或禁止调用的规则；
- 工具调用结果由谁消费；
- 当前 Agent 明确不可用但相邻节点可用的工具。

### 输出与异常

- 自然语言、结构化输出、工具调用或组合；
- 输出格式和字段；
- 下游如何解释结果；
- 拒绝、信息不足、超时、工具失败和模型异常如何处理。

### 运行环境门禁

如果上述任一关键事实缺失，并会导致 Skill 猜测工具、消息、状态、输出或异常行为，则停止对应提示词生产，生成知识补全请求。

## 二、核心门禁 B：关键执行时机上下文契约

仅有“系统中存在这些消息”还不够。Skill 必须针对每个关键执行时机，明确模型在该时刻实际收到什么。

### 每个执行时机的上下文契约

- 时机名称与触发条件；
- 消息组成及实际顺序；
- 每条消息的 role / 类型；
- 内容来源；
- 注入方；
- 注入时机；
- 是否每轮重复、仅首次出现、循环时重注入或条件注入；
- 动态字段名和含义；
- 当前可见工具；
- 当前不可见信息；
- 输出去向。

建议用接近真实运行的形式表达：

```text
执行时机：第二门禁判定

1. system：MainAgent 底座
2. task：资金安全问题判定主 prompt
3. context：允许使用的对话历史 / 当前消息
4. user：经边界标签包裹的用户原文
5. reminder：内部循环时条件性再次注入
6. tools：report_out_of_scope schema
```

以上只是格式示例，具体顺序必须来自当前项目知识，不能写死到通用 Skill。

## 三、概念引用绑定表

为避免“不存在的代词”，Skill 扫描每条提示词中的概念引用，并记录：

| 引用词 | 需要的定义 | 定义来源 | 运行时承载位置 | 当前时机是否可见 | 结论 |
|---|---|---|---|---|---|
| 七要素 | 七个维度及其语义 | 知识卡 | 当前 task / 动态 context / 已继承底座 | 是/否 | 已绑定/未绑定 |
| 当前事件 | 事件状态结构及当前值 | 运行时状态 | `event_context` 等明确字段 | 是/否 | 已绑定/未绑定 |
| 上述规则 | 被引用规则的具体范围 | 当前上下文中的消息 | 明确消息段 | 是/否 | 已绑定/未绑定 |

### 引用绑定成立条件

概念必须满足至少一项：

- 在当前 prompt 中明确定义；
- 在本次确定会叠加的上游 prompt 中定义；
- 由运行时以明确字段、结构或消息注入；
- 由模型本次可见的工具 schema 定义。

“知识库里有这张卡”不能单独证明引用成立，因为知识库是生成来源，不会自动进入模型运行上下文。

## 四、硬性校验

以下任一情况发生，对应提示词不通过：

- 未形成 Agent 运行环境说明；
- 未形成关键执行时机上下文契约；
- 消息来源、注入方或时机不明确；
- 使用了运行时不可见的工具；
- 工具 schema 与提示词描述不一致；
- 引用的概念只有名称，没有当前上下文可见的定义；
- 使用“上述、该事件、按前述规则”等表达但无法唯一定位；
- 动态状态字段不存在或语义不一致；
- 输出格式无法被下游消费。

这些属于一票否决，不进入语气或简洁度评分。

## 五、在分阶段工作流中的位置

### 阶段 2：知识发现

取得形成两份核心产物所需的知识；缺失则进入知识补全。

### 阶段 4：架构设计

正式生成：

1. Agent 运行环境说明；
2. 每个关键时机的上下文契约；
3. 概念引用绑定表。

三者随提示词架构一起交给前台人员确认。

### 阶段 5：逐单元生成

每生成一条 prompt，都重新检查它只引用当前执行时机可见的内容。

### 阶段 6：集成校验

按上下文契约拼装完整消息，检查各 prompt 组合后的真实可见性和工具能力。

## 六、与资金安全顾问案例的对应

- MainAgent：需要明确所有门禁与回复任务是否都实际叠加该 system prompt；
- 第二门禁：“结合上下文”必须说明具体包含哪些历史消息或状态，不能只写这四个字；
- 第三门禁：引用七要素时，需要在当前 prompt 或注入上下文中获得明确的七项定义；
- 回复 task：`memory_trails.event_context` 必须真实注入，并且字段含义与七要素对应；
- reminder/anchor：需要明确它们以何种消息类型、在哪个循环或执行时机注入；
- 工具：三个 report 工具和 `fund_security_event_write` 必须以真实 schema 对模型可见。

当前知识库描述了其中大部分内容，但例如第二门禁“结合上下文”具体包含什么、各消息的实际拼接顺序等仍未完全明确。按新门禁，这些内容需要补全后才能确认提示词运行上下文正确。
