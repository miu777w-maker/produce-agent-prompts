# Skill 任务流程分离 V0

> 日期：2026-08-11  
> 状态：用户已确认原则，待并入正式 Skill。

## 一、为什么必须分离

“检验”“新建”“修改/优化”虽然共享知识发现和六项核心基线，但目标、授权边界、阶段产物和完成条件不同。混成一个流程会导致：

- 检验过程中未经授权修改；
- 现有错误体系锚定新建方案；
- 修改任务被误当作从零生成；
- 报告与正式 prompts 混在聊天或同一产物中；
- 无法判断某次任务究竟完成了审查、设计还是修复。

## 二、启用后的四种任务

### 1. Inspection：检验已有提示词

目标：验证生产范围、prompt 清单、单元质量、系统组合、知识忠实度和运行时真实性。

输入：项目目标、权威知识库与运行时事实、现有 prompts/evals、检验范围。  
输出：独立 Markdown 检验报告、知识补全请求（如需）、后续建议。  
禁止：自动修改 prompts/evals/知识库。  
完成：报告文件落盘并返回路径。

### 2. Creation：新建提示词体系

目标：从目标和知识库推导或依据确认清单，新建一个可接入、可评测的 prompt 版本。

输入：目标、范围、不可改变要求、权威知识；人员可知道或不知道 prompt 清单。  
输出：新 prompts、同步 evals、来源映射、六项门禁产物、运行时集成契约和外部评测交接包。  
禁止：把现有草稿默认当作正确架构；如作为参考，明确其证据等级。  
完成：静态通过并进入外部评测；只有获得外部证据和最终确认后成为可用版本。

### 3. Revision：修改或优化已有提示词

目标：根据明确变更需求、知识变化或 inspection 报告，修复受影响体系并形成新版本。

输入：变更目标或检验发现、现有版本、知识与运行时事实、修改授权。  
动作：先归因和影响分析，再确定新增、修改、合并、拆分、删除和无需变化项；保留不受影响内容。  
输出：新版本 prompts/evals、差异说明、来源和版本映射、回退位置、更新后的契约及评测交接。  
禁止：直接在 inspection 中启动；不得无证据重写整套系统。  
完成：新版本通过静态检查并进入外部评测，旧版本仍可追溯或回退。

### 4. Eval-only：编写或补齐评测

目标：为已有、已确认范围的 prompts 设计或补齐 evals，不擅自重写 prompt。

输入：prompts、知识来源、运行时契约、评测目标。  
输出：evals、rubric/judge、测试集要求和外部交接包。  
遇到上游问题：形成发现并建议启动 inspection 或 revision，不在当前流程越权修改。

## 三、流程之间的交接

```text
Inspection ──报告──> 人员决定是否启动 Revision
Creation ──新版本──> 外部评测 ──失败归因──> Revision
知识/规则变化 ──影响分析──> Revision
Creation 或 Revision ──缺 eval──> Eval-only
```

流程交接必须由用户明确启动或授权。上一个流程的输出作为下一个流程输入，但状态、检查点和产物目录分开。

## 四、对话与文件输出规则

- 完整 inspection 报告、prompt、eval、契约和差异说明必须写入独立文件；
- 对话只提供结果摘要、关键阻塞、文件路径、当前状态和下一决策；
- 不把长篇正式产物只留在聊天记录；
- 每次任务保持独立任务标识、检查点、目录和版本；
- Revision 不覆盖旧版本，保留安全差异和回退位置。

## 五、待实验项

当体系/清单错误时继续审查现有 prompt 内容，验证能否稳定区分：

1. 由错误体系派生的问题；
2. prompt 单元自身仍然成立的问题；
3. 重构后必须重新检验的问题。

实验成功标准：报告能帮助后续 Revision 减少遗漏，而不会把错误架构下的局部结论错误固化到新版本。
