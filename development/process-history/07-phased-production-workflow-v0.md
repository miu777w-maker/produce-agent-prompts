# 系统 Agent 提示词 Skill：分阶段生产工作流 V0

> 主线步骤 4 讨论稿。  
> 设计目标：不一步生成；每阶段单独操作、保存产物、通过门禁后继续，支持暂停、分支取证与恢复。

## 一、稳定生产原则

1. **一阶段一种主要判断**：不要在同一轮同时完成需求解释、知识检索、架构决定和逐字编写。
2. **一阶段一个主要产物**：后续阶段只基于已经保存并确认的上游产物推进。
3. **门禁未过不前进**：关键输入缺失时停止提示词生产，转入知识补全分支。
4. **需求事实与 Skill 建议分开**：Skill 可以指出需求遗漏，但不能静默改变交付范围。
5. **提示词与评测同步**：每完成一个提示词单元，同时形成对应的硬检查、rubric 或 judge prompt。
6. **逐单元生成**：即使任务包含整套系统提示词，也按架构依赖顺序逐个完成，而不是一次生成全部文件。
7. **持续保存状态**：每阶段记录当前主线、已完成产物、未决事项、分支任务和恢复入口。

## 二、建议的八个阶段

### 阶段 0：启动与恢复

**目的**：确定这是新任务还是继续已有任务，并找回上次主线。

**动作**：

- 读取原始需求和已有阶段产物；
- 确认当前知识库契约、话题和产物目录；
- 确认本次是整套系统还是局部提示词任务；
- 如果是恢复任务，读取最后检查点，不重做已确认阶段。

**产物**：任务状态卡。

**门禁**：原始需求与当前回归点可定位。

---

### 阶段 1：需求解析

**目的**：回答“这次为什么写、目标系统和范围是什么”，并识别明确清单、目标驱动或变化驱动模式。

**动作**：

- 保留原始需求；
- 有明确清单则提取；没有则登记为目标驱动发现，不要求人员现场设计提示词清单；
- 区分需求明确指定、知识库已有体系、Skill 候选建议；
- 标出新建、重写、更新和非本次范围。

**产物**：任务目标与范围、可选的已有提示词清单、任务入口模式。

**门禁**：生产目标、系统范围、不可改变要求和交付类型明确；人员是否知道 prompt 清单不构成阻塞。

---

### 阶段 2：知识发现与覆盖检查

**目的**：围绕任务清单，从知识库取得生成所需的最小充分知识。

**动作**：

- 话题优先定位相关卡组；
- 读取综合卡、根卡、原子卡及引用关系；
- 用搜索索引补找术语、工具、上下文、约束和评测知识；
- 按五类输入建立任务覆盖图；
- 在目标驱动模式中识别执行单元、规则作用域和候选提示词；
- 默认信任入库知识，只检查明显错误和显式限定。

**产物**：知识覆盖图 + 发现的缺口/冲突。

**门禁**：每个目标提示词的五类关键输入都有知识来源；不存在未解决的关键错误或冲突。

---

### 阶段 3：知识补全（条件分支）

**目的**：补齐阶段 2 发现的阻塞信息。

**动作**：

- 为前台人员生成知识补全请求；
- 建议由项目人员、后端 Agent、前端 Agent或其他来源补充；
- 等待结果带来源回写知识库；
- 重新检索并更新覆盖图。

**产物**：补全请求、回写知识卡或未解决阻塞记录。

**门禁**：关键缺口已经补入知识库并重新通过阶段 2。未通过时不生成提示词。

**回归点**：补全完成后回到阶段 2，不直接进入架构或编写。

---

### 阶段 4：提示词架构设计

**目的**：决定每条规则由哪个提示词或运行时载体承担。

**动作**：

- 形成提示词架构清单；
- 在目标驱动或变化驱动模式中形成最终建议的提示词生产任务清单；
- 为每个执行单元形成 Agent 运行环境说明；
- 为每个关键执行时机建立上下文契约；
- 建立概念引用绑定表，消除运行时不存在的代词或概念；
- 形成业务与角色行为契约；
- 形成提示词职责与信息可见性矩阵；
- 形成关键约束与注意力安排；
- 更新知识疑点与冲突检查报告；
- 为每个提示词单元形成运行时集成契约，明确消息装配、变量注入、工具、输出解析和异常路径；
- 分配 system、task、reminder/anchor、动态上下文和工具 schema；
- 检查引用是否在真实上下文中成立；
- 区分无效重复与有目的的重新注入；
- 把知识卡规则映射到目标提示词和对应评测。

**产物**：架构清单 + 原始输入六项核心门禁产物 + 规则归属矩阵。

**门禁**：原始输入六项核心门禁全部明确通过；需求事实与 Skill 建议已区分。

---

### 阶段 5：逐单元生成提示词与评测

**目的**：按照架构依赖顺序，稳定完成每个提示词单元。

**建议顺序**：

1. 系统底座；
2. 各独立任务主提示词；
3. 与主提示词配对的 reminder/anchor；
4. 对应 rubric、硬检查和 judge prompt。

每次只处理一个“提示词单元”。一个单元通常是：

- 单独的 system prompt + 对应评测；或
- task + reminder/anchor + 对应评测；或
- 用户需求明确指定的其他最小可独立验收组合。

**每个单元的动作**：

- 读取该单元对应的架构项和来源卡；
- 先生成规则骨架，再生成逐字提示词；
- 标注来源卡和路径；
- 同步抽取硬检查与软评测；
- 做单元自检；
- 保存后再进入下一个单元。

**产物**：单个提示词文件及其对应 eval。

**门禁**：该单元通过职责、上下文、引用、工具、知识、表达、简洁度和评测映射检查。

---

### 阶段 6：系统集成校验

**目的**：完成静态组合检查，并生成外部行为评测交接包；收到结果后诊断组合运行是否正确。

**动作**：

- 按真实加载顺序模拟各关键执行时机；
- 检查底座与任务叠加后的重复、冲突和优先级；
- 检查动态上下文、工具 schema、reminder/anchor 是否在正确时机可见；
- 检查上游输出是否满足下游输入；
- 定义代表性路径、边界案例和异常路径的外部执行要求；
- 检查 prompts 与 evals 是否一一对应。

**产物**：静态集成校验报告 + 外部评测交接包；结果返回后补充行为评测诊断与必要修改清单。

**门禁**：静态检查通过后可进入“待外部评测”；只有收到可追溯结果且所有关键路径通过，才可标记行为校验完成。

---

### 阶段 7：交付与可维护性检查

**目的**：形成可使用、可追溯、可更新的完整交付。

**动作**：

- 检查产物目录和命名；
- 检查每个 prompt/eval 的知识卡来源；
- 生成提示词总览、加载顺序和依赖说明；
- 输出运行时集成契约和代码侧实现/核查请求；
- 记录未决的非阻塞事项；
- 保存最终任务状态和后续更新入口。

**产物**：正式 prompts、同步 evals、来源映射、运行时集成契约、必要的代码侧交接请求、总览与最终校验结果。

**门禁**：需求清单中的每项交付均已完成，并可追溯到原始需求和知识库。

## 三、暂停与恢复机制

每个阶段结束时写入检查点：

- 当前阶段与状态：未开始 / 进行中 / 等待补全 / 已通过；
- 本阶段输入；
- 已生成并保存的产物路径；
- 已确认判断；
- 未决事项；
- 当前分支及负责人；
- 下一步动作；
- 应回归的主线阶段。

恢复时先读检查点，只继续未完成步骤，不重新解释已冻结的原始需求。

## 四、突发需求与中断处理

阶段定义用于稳定生产，不应让 Agent 对用户的新信息失去理解能力。收到突发需求时，Skill 先判断其性质：

### 1. 当前阶段补充

新信息只是补充当前正在处理的内容：纳入当前阶段产物，继续当前门禁。

### 2. 上游修正

新信息修改了已经确认的需求、知识或架构：记录修正来源，回到最早受影响的阶段，重新检查其下游产物；不只修改最后生成的提示词。

### 3. 临时分支

新需求与主线相关，但可以独立处理：

- 保存当前阶段和回归点；
- 建立分支目标与待办；
- 完成分支并记录结论；
- 判断结论是否影响主线已有产物；
- 回到原阶段继续。

### 4. 任务替换

用户明确取消或替换原任务：停止原主线，保留已有记录，建立新的原始需求与阶段状态；不能把新任务混入旧任务产物。

### 5. 无关插入

如果只是短暂的无关问答，回答后恢复当前检查点，不改变生产任务范围。

### 中断后的最小状态提示

Skill 应明确告诉用户：

- 当前信息被判断为什么类型；
- 哪个阶段受到影响；
- 是否开启分支或回退；
- 处理后将回到哪里。

## 五、为什么不一步生成

一步生成会把多种错误混在一起：

- 需求范围理解错误；
- 知识缺失或冲突；
- 提示词职责划分错误；
- 运行时上下文假设错误；
- 逐字表达错误；
- rubric 与提示词脱节。

分阶段后，每种错误在进入下游前被发现，并且能明确回到产生它的阶段修正。

## 六、与原始输入的对应

- 运行环境与消息 → 阶段 2、4、6；
- 关键时机上下文与不存在的代词 → 阶段 4、6；
- 业务背景、角色、语气与行为 → 阶段 2、5；
- 职责、不重复、渐进式披露 → 阶段 4、6；
- Anchor 类重点提醒 → 阶段 4、5、6；
- 可疑知识错误 → 阶段 2、3、5、6；
- 稳定生产与回归主线 → 全阶段门禁和检查点。

## 七、当前建议

将该 Skill 定义为“多阶段工作流 Skill”，而不是一次性生成器。默认一次交互推进一个阶段；阶段内部遇到阻塞则进入知识补全分支，补全后回到原门禁。

八阶段定义当前作为 V0。实际使用中可根据真实任务调整阶段内部动作或合并非关键操作，但不得跳过需求确认、关键输入就绪、架构确认和最终校验这些核心门禁。

## 八、已确认的人机确认点

默认只在三个关键决策点要求前台人员显式确认：

1. 阶段 1 结束：确认生产目标、系统范围和不可改变要求；如已有提示词清单则一并确认；
2. 阶段 4 结束：确认最终提示词生产清单、架构、职责与加载时机；
3. 阶段 7 结束：确认最终交付满足需求清单。

其他阶段由 Skill 自动推进；发现关键知识缺口、重大冲突或突发需求改变上游结论时暂停。
