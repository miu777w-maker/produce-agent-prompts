# 系统 Agent 提示词生产 Skill：校验模型 V0

> 主线步骤 5 产物。  
> 目标：验证的不只是模型最终回复，还包括需求理解、知识覆盖、提示词架构、逐字内容、运行时组合和长期同步。

## 一、校验分层

### 环境职责说明

知识库中的 Skill 可以完成阶段门禁、静态校验、评测设计和结果诊断，但不直接执行需要真实模型、工具或运行时的行为评测。行为评测由后端 Agent 或专门评测环境执行。

### 层 1：阶段门禁

检查每个生产阶段是否具备进入下一阶段的条件，防止错误一路传递到最终 prompt。

### 层 2：单个提示词单元校验

检查一个 system、task + reminder/anchor 或其他最小提示词单元，是否忠实表达知识、能在真实上下文中执行，并有配套评测。

### 层 3：系统组合校验

把提示词按真实加载顺序叠加，检查跨层冲突、上下游契约、动态上下文和长对话行为。

### 层 4：交付同步校验

检查需求、知识库、prompts 和 evals 之间是否可以相互追溯，后续修改是否发生漂移。

## 二、三种校验方式

### A. 确定性检查

能够明确判断通过/失败的内容，不交给 judge 主观评分。例如：

- 文件、frontmatter、路径和来源标注是否存在；
- 需求清单中的提示词是否全部生成；
- 工具名称、字段、枚举和结构是否与契约一致；
- 必须调用的工具是否调用；
- 输出 JSON 是否符合 schema；
- 追问是否超过规定数量；
- prompt 与 eval 是否一一对应；
- 引用的知识卡和运行时概念是否存在。

### B. 行为评测

需要执行模型并观察行为，包括：

- 判定取向是否符合要求；
- 边界案例是否稳定；
- 语气和角色是否合适；
- 长对话是否漂移；
- prompt injection 或用户诱导下是否守住边界；
- 多条规则同时出现时是否正确选择路径。

行为评测再分：

- **可验证项 V**：根据黄金答案、工具调用或结构化行为判断；
- **judge 项 J**：对语气、取向、简洁度等按 rubric 打分。

Skill 负责生成这些评测定义与交接要求；没有收到外部执行结果前，状态只能是“待外部评测”。

### C. 人工确认

只保留在产品与业务判断点：

- 提示词生产任务清单；
- 提示词架构与职责划分；
- 最终交付是否满足原始需求。

知识缺口需要项目人员作决定时，也属于临时人工阻塞，而不是普通评分项。

## 三、阶段门禁检查

| 阶段 | 必须检查 | 不通过时回到 |
|---|---|---|
| 启动与恢复 | 原始需求、已有产物、当前阶段和回归点可定位 | 重新建立任务状态，不进入需求解析 |
| 需求解析 | 提示词清单、职责、范围、交付和验收明确；需求事实与 Skill 建议分开 | 留在需求解析或发起需求补充 |
| 知识发现 | 五类输入覆盖；话题和搜索已检查；无关键缺口、明显错误或未解决冲突 | 知识补全分支 |
| 知识补全 | 返回信息已带来源进入知识库，并能重新检索 | 继续补全或回知识发现 |
| 架构设计 | 每个执行时机有上下文快照；规则有主要归属；引用可见；重复有理由 | 回到架构设计；如因知识缺失则回知识发现 |
| 单元生成 | 知识忠实、职责正确、工具契约正确、来源明确、对应 eval 存在 | 修改当前单元；如上游错误则回相应阶段 |
| 系统集成 | 加载顺序、上下游、动态上下文、工具、异常和关键路径通过 | 回架构或具体单元 |
| 交付 | 原始需求全部覆盖；prompts/evals/来源映射同步；无关键未决项 | 回到最早受影响阶段 |

## 四、单个提示词单元的七类校验

### 1. 需求忠实度

- 是否对应任务清单中的明确目标；
- 是否擅自新增、删除或改变职责；
- Skill 建议是否仍被清楚标记，而非伪装成需求。

### 2. 知识忠实度

- 每条关键规则是否能追溯到知识卡；
- 是否引入知识库中不存在的业务判断；
- 是否保留卡片中的“非最终、例外、适用范围”等限定；
- 是否发现明显知识错误、冲突或不一致。

默认信任入库知识，不要求逐条外部证明；这里检查的是提示词有没有误读、漏掉限定或自行发明。

### 3. 运行时真实性

- 触发时机是否真实；
- prompt 叠加关系是否真实；
- 消息、状态、工具和 schema 是否真实可见；
- 提示词是否引用了运行时不存在的概念；
- 输出是否能被下游实际消费。

### 4. 职责与渐进式披露

- 当前提示词只承担自己的职责；
- 是否放入了其他层负责的业务规则；
- 是否缺少执行本职任务所需的关键定义；
- 重复内容是否有重新注入或自包含理由；
- reminder/anchor 是否只保留高价值重点。

### 5. 指令可执行性

- 目标、步骤、边界、输出是否明确；
- 指令是否互相冲突；
- 含糊词、代词和跳步是否能够在当前上下文中解析；
- 缺失、矛盾、工具失败和异常时是否有处理规则；
- 自由度是否与任务风险匹配。

### 6. 注意力与表达

- 关键约束是否位于模型真正需要关注的位置；
- 长任务是否有必要的 reminder/anchor；
- 角色、语气和行为约束是否符合知识库；
- 表达是否简洁，是否因过度重复稀释重点。

### 7. 评测完整性

- 每条“必须/不得”是否有可验证项；
- 取向、语气和主观质量是否有独立 rubric；
- 安全、合规、核心路径和工具契约是否设置一票否决；
- 条目是否正交、可独立判断；
- 测试输入是否包含相应失败面。

## 五、测试案例按失败面选择

Skill 不机械地给每条 prompt 生成同一套案例。根据该提示词可能失败的方式选择：

- **正常案例**：典型输入和预期行为；
- **边界案例**：规则边缘、相邻类别和临界状态；
- **模糊案例**：验证保守/放行/追问等业务取向；
- **冲突案例**：本轮信息与已有状态矛盾；
- **缺失案例**：关键字段、历史或上下文缺失；
- **工具案例**：该调、不该调、参数错误、工具异常；
- **对抗案例**：prompt injection、越权诱导、绕过边界；
- **长对话案例**：验证 reminder/anchor 的漂移控制；
- **组合案例**：多条规则同时触发，验证优先级和路径选择；
- **上下游案例**：上游输出边界值是否能被下游正确消费。

## 六、一票否决的使用原则

只有破坏系统正确性或安全性的规则才设一票否决，例如：

- 关键工具未调用或调用结构非法；
- 核心路由/状态机路径错误；
- 越过明确安全、合规或业务禁区；
- 引用了运行时不存在的关键上下文；
- 关键知识缺失仍生成确定性提示词；
- prompt 与实际执行单元不匹配。
- Agent 运行环境说明或关键执行时机上下文契约缺失；
- 提示词出现无法绑定到当前运行时上下文的概念引用或“代词”。

语气略显生硬、个别冗余等不应与安全错误同等处理，可进入评分或修改建议。

## 七、系统组合校验

单个文件通过后，按每个关键执行时机拼出模型实际收到的完整上下文，并检查：

1. system、task、reminder/anchor 的规则是否冲突；
2. 同一规则多次出现时优先级是否清楚；
3. 动态状态字段和概念名称是否一致；
4. 工具 schema 与 prompt 使用方式是否一致；
5. 上游输出是否满足下游输入；
6. 并行任务是否错误共享或依赖彼此信息；
7. 异常、拒绝和超时路径是否与程序处理一致；
8. 长对话或复杂输入下，关键约束是否仍有效。

## 八、需求—知识—提示词—评测追溯

最终维护一条四段追溯链：

```text
原始需求条目
  → 知识库卡片与项目约定
    → prompt 文件及具体规则
      → eval 条目与测试案例
```

### 漂移检查

- 知识卡更新但相关 prompt 未更新；
- prompt 更新但来源映射未更新；
- prompt 规则变化但 eval 未同步；
- eval 仍在评旧规则；
- 需求范围变化但架构清单未重审。

发现漂移时回到最早变化的阶段，而不是只修改最后一个文件。

## 九、校验报告的最小输出

- 校验范围和版本；
- 确定性检查结果；
- 行为评测结果；
- 一票否决项；
- 明显知识疑点；
- 未决的非阻塞问题；
- 失败项对应的回退阶段；
- 是否允许进入下一阶段。

如果行为评测尚未执行，报告必须明确区分“静态校验通过”和“外部行为评测待执行”，不得合并为“校验通过”。

## 十、资金安全顾问案例验证

当前项目已有评测材料支持此模型：

- 门禁 rubric 检查工具调用、verdict 结构、判定方向和模糊放行取向；
- 回复 task 把工具流程、状态机路径、完整度、追问数量和建议结构做成可验证项；
- task judge 对五禁区设置一票否决，再评事实、完成、指令、语气和简洁度；
- anchor 用 10+ 轮对话和后段越界诱导测试漂移。

案例同时提示：评测不只是列规则，还需要实际黄金集、运行记录和阈值；如果这些关键材料缺失，不能宣称行为已验证通过。
