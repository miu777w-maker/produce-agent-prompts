## 一、最原始任务

基于用户收到的《编写一个系统 Agent 提示词的注意事项》，共同设计一个 Skill，用于规范从项目知识库稳定生产系统 Agent prompts 与 evals 的过程。

原始输入全文及用户修正保存在：

- `00-original-task-input.md`

原始输入始终是最高层指导和最终验收基线。

## 二、Skill 的最终定位

- 主要运行在类似 `Zettel_KDB` 的项目知识库中；
- 通过知识库话题优先发现相关知识，再沿根卡、原子卡、引用和搜索索引补足；
- 入库内容默认真实，只有明显错误、冲突、断链、版本异常或显式“非最终”时提出；
- 既支持整套系统提示词，也支持局部提示词；
- 既支持人员给出明确 prompt 清单，也支持人员只给目标、Skill 从知识库推导 prompt 清单；
- 生成正式 prompts、同步 evals、来源映射、运行时集成契约和外部评测交接包；
- 不直接实现项目后端/前端代码，不直接执行真实行为评测；这些交给代码侧 Agent 或评测环境；
- 关键知识缺失时绝不生成提示词，只输出知识补全请求。

## 三、三种任务入口

1. **明确清单模式**：人员已给出 prompts 与职责，Skill 验证并生产。
2. **目标驱动模式**：人员只给系统/产品目标，Skill 从知识库识别执行单元、规则作用域和提示词候选，再交前台人员确认。
3. **变化驱动模式**：知识、schema、流程或业务规则变化，Skill 先做影响分析，再更新受影响 prompts/evals。

## 四、分阶段工作流 V0

1. 启动与恢复；
2. 需求目标解析与入口识别；
3. 知识发现与覆盖检查；
4. 条件性知识补全分支；
5. 提示词清单与架构设计；
6. 逐单元生成 prompt + eval；
7. 静态系统集成校验与外部评测交接；
8. 交付与可维护性检查。

### 三个人工确认点

1. 生产目标、系统范围和不可改变要求；
2. 最终提示词清单、职责、架构、上下文和加载时机；
3. 最终交付。

其他阶段自动推进；遇关键缺口或上游变化暂停。

## 五、原始输入六项核心门禁

正式 Skill 必须明确产出并检查：

1. **Agent 运行环境说明**；
2. **关键执行时机上下文契约 + 概念引用绑定表**；
3. **业务与角色行为契约**；
4. **提示词职责与信息可见性矩阵**；
5. **关键约束与注意力安排**；
6. **知识疑点与冲突检查报告**。

六项不能分散隐藏；即使“未发现问题”也要明确输出结论。关键项不通过时不生成。

## 六、运行时与代码层边界

Skill 必须输出运行时集成契约，覆盖：

- prompt 加载节点、message role 和装配顺序；
- 动态变量、状态、历史和知识注入；
- 工具名称/schema/调用条件/结果消费者；
- 输出结构与 parser；
- reminder/anchor 注入钩子；
- 异常路径；
- prompt/schema/code/eval 版本对应。

实际代码修改交给后端或前端 Agent；实现事实回写知识库后，Skill 复核契约。

## 七、知识补全机制

Skill 发现关键缺口后，把请求交给前台人员。前台人员选择：

- 项目人员补充业务决策；
- 后端 Agent 获取编排、消息、工具、状态和运行事实；
- 前端 Agent 获取用户输入、页面状态、交互和接口事实；
- 其他明确来源。

补充内容必须带来源进入知识库。Skill 重新检索并回到知识就绪检查，不能直接跳到 prompt 编写。

## 八、校验与外部评测

- 确定性检查：文件、路径、来源、schema、工具、变量、结构和 prompt/eval 对应；
- 行为评测定义：正常、边界、模糊、冲突、缺失、工具、对抗、长对话、组合、上下游案例；
- 后端 Agent 或评测环境实际执行；
- 未收到结果时状态只能是“待外部评测”；
- 结果返回后先归因到需求、知识、架构、prompt、eval 或运行环境，再决定回退阶段；
- 稳定结论建议入知识库，原始日志通常留评测产物区；具体遵循项目契约。

## 九、突发需求与主线恢复

新消息需判断为：当前阶段补充、上游修正、临时分支、任务替换或无关插入。

临时分支必须保存回归点，结束后评估对主线产物的影响，再返回原阶段。
