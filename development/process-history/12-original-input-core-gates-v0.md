# 原始输入六项核心门禁总表 V0

> 目的：确保原始输入中的每一项都在正式 Skill 中成为明确产物和门禁，而不是分散在流程说明里被弱化。

## 一、六项核心产物

| 原始输入要求 | Skill 的明确产物 | 不通过条件 |
|---|---|---|
| Agent 运行时工作环境 | Agent 运行环境说明 | 关键工具、消息、状态、输出或异常路径需要猜测 |
| 关键执行时机上下文，避免不存在的代词 | 执行时机上下文契约 + 概念引用绑定表 | 消息组成/注入不明，或概念在当前上下文不可见 |
| 业务背景、角色、语气与行为约束 | 业务与角色行为契约 | 目标 Agent 的业务目标、身份、服务边界或关键行为规则缺失 |
| 各提示词作用与职责，不重复、渐进式披露 | 提示词职责与信息可见性矩阵 | 职责重叠/遗漏、无理由重复、越权加载或关键上下文缺失 |
| 在关键位置提醒业务任务约束，如 Anchor | 关键约束与注意力安排 | 高风险约束没有明确归属、注入位置或验证方式 |
| 校验可疑知识错误 | 知识疑点与冲突检查报告 | 存在影响当前提示词的明显错误、冲突或显式非最终内容未解决 |

六项产物必须逐项给出，即使某项结论是“未发现问题”，也不能省略该检查。

“Agent 运行环境说明”还必须形成代码可执行的“运行时集成契约”。Skill 不直接实现项目代码，但需要明确消息装配、变量注入、工具注册、输出解析、异常处理和版本对应，供代码侧 Agent 实现与核验。

## 二、核心门禁 3：业务与角色行为契约

针对本次提示词任务涉及的角色，明确：

- 产品或业务目标；
- 服务对象；
- Agent 身份与专业定位；
- 要完成的业务结果；
- 明确不做什么；
- 目标优先级；
- 行为边界与安全边界；
- 语气、表达对象和沟通要求；
- 领域术语及必要定义；
- 信息不足、用户拒绝、冲突或越界时的行为；
- 来源卡及其显式限定。

### 不通过条件

- 角色身份来自“非最终”材料且影响当前 prompt；
- 只有语气形容词，没有可执行行为边界；
- 业务目标、服务范围和拒绝范围相互矛盾；
- 把相邻项目角色直接复制到当前项目；
- 角色规则只存在于知识库，但没有分配到实际可见的 prompt 层。

## 三、核心门禁 4：提示词职责与信息可见性矩阵

对每个 prompt/运行时载体记录：

| 载体 | 唯一主要职责 | 必须知道 | 可以知道 | 不应知道 | 上游 | 下游 |
|---|---|---|---|---|---|---|
| system |  |  |  |  |  |  |
| task |  |  |  |  |  |  |
| reminder/anchor |  |  |  |  |  |  |
| 动态上下文 |  |  |  |  |  |  |
| tool schema |  |  |  |  |  |  |

### 必须检查

- 每条关键规则是否有一个主要责任载体；
- 是否有多个 prompt 无理由承担相同职责；
- 某条规则是否无人负责；
- 当前 Agent 是否看到了其他执行单元才需要的细节；
- 为了省 token 删除的信息是否导致当前任务无法执行；
- 重复是同一次上下文的浪费，还是新时机的必要重注入；
- 整套系统任务与局部提示词任务是否采用了不同的读取范围。

### 不通过条件

- MainAgent 承载了局部门禁的具体判定逻辑；
- 门禁加载了回复阶段全部业务策略但不使用；
- task 依赖底座规则但实际不继承；
- reminder 复制整份主 prompt，没有注意力目的；
- 动态状态被错误写死进静态 prompt。

## 四、核心门禁 5：关键约束与注意力安排

不是所有重要规则都需要 Anchor。Skill 必须先建立关键约束清单，再判断如何让模型在正确时机关注。

### 每条关键约束记录

- 约束内容；
- 业务或安全影响；
- 适用执行单元；
- 主要归属 prompt；
- 最容易失效的时机；
- 失效原因：长对话、复杂输入、循环、工具调用、多个规则竞争等；
- 注意力手段：结构位置、明确标题、重复提醒、reminder、anchor、工具强制、schema 或程序门禁；
- 注入方与注入时机；
- 是否需要重复，以及重复理由；
- 对应测试方式。

### Anchor/reminder 使用门禁

只有当运行时支持注入，且约束重要、容易漂移、重复收益高于成本时才设置。不能因为“Anchor 看起来专业”就新建。

### 不通过条件

- 关键安全或任务取向只埋在长 prompt 中，没有明确关注位置；
- 设置了 Anchor，但系统不会在声称的时机注入；
- Anchor 与 task 规则冲突；
- Anchor 承载大量新业务逻辑，而不是稳定关键约束；
- 没有为 Anchor/reminder 设计长对话或复杂输入验证。

## 五、核心门禁 6：知识疑点与冲突检查报告

项目约定知识库内容默认真实，所以该检查不是全面事实审计，而是有针对性地扫描明显问题。

### 检查范围

- 同一概念在相关卡片中定义不一致；
- 流程顺序、职责或工具调用规则冲突；
- 文件、字段、工具或消息名称前后不一致；
- 引用目标不存在或无法定位；
- 时间、版本、数量等出现明显异常；
- 卡片明确标注“非最终、待确认、来自旧项目”；
- prompt 引入知识库没有的业务规则；
- 知识更新后 prompt/eval 未同步。

### 报告格式

- 疑点内容；
- 相关卡片或产物；
- 为什么可疑；
- 影响哪些 prompt/eval；
- 是否关键阻塞；
- 建议补充方；
- 解决后回到哪个阶段。

如果未发现明显疑点，也要输出“已检查，未发现影响本次任务的明显知识问题”，而不是省略。

## 六、六项门禁在阶段中的位置

### 阶段 2：知识发现与覆盖

准备六项产物需要的知识，形成业务与角色行为契约、知识疑点报告初版。关键缺失进入知识补全。

### 阶段 4：架构设计

正式形成：

1. Agent 运行环境说明；
2. 执行时机上下文契约；
3. 概念引用绑定表；
4. 业务与角色行为契约；
5. 提示词职责与信息可见性矩阵；
6. 关键约束与注意力安排；
7. 更新后的知识疑点与冲突报告。

前台人员确认架构时，应看到这组明确产物，而不是只看到一张 prompt 文件清单。

### 阶段 5：逐单元生成

每个提示词单元逐项引用上述产物，不能绕过。

### 阶段 6：集成校验

重新检查六项门禁在真实提示词组合、动态上下文和工具环境中是否仍成立。

## 七、用户后续补充形成的另外两个前置门禁

它们不是原始六项，但已经由用户明确加入：

### A. 任务目标与提示词生产清单

先从需求中确认生产目标与范围。人员已知 prompt 清单时直接提取；人员不知道时，由 Skill 从知识库推导候选清单和职责，再交前台人员确认。

### B. 知识输入就绪与补全门禁

关键知识缺失时不生成；向前台人员提出补全请求，内容回写知识库后重新检查。

因此，正式 Skill 的前置门禁总结构是：

```text
任务目标与入口模式
  → 知识输入就绪
    → 原始输入六项核心门禁
      → 确认提示词生产清单与架构
        → 逐单元提示词与 eval 生产
```
