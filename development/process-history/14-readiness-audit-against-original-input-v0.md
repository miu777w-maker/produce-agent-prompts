# 正式 Skill 编写前就绪审计 V0

> 审计基线：`00-original-task-input.md` 中的最原始输入。  
> 结论：原始输入与用户后续明确补充均已形成可执行设计，足够进入正式 Skill 编写。

## 一、最原始输入逐条倒查

### 1. 是否介绍 Agent 运行时工作环境

**原始要求**：工具、可能收到的用户或系统消息等。

**当前设计**：

- Agent 运行环境说明；
- 运行时集成契约；
- 工具/schema、消息 role、状态、历史、输出消费者和异常路径；
- 知识库缺失时向代码侧 Agent 发起补全。

**对应文件**：`11-runtime-and-context-core-gates-v0.md`、`13-code-layer-boundary-v0.md`。

**结论**：已覆盖，并提升为硬门禁。

### 2. 是否明确关键执行时机的上下文组成，避免不存在的代词

**原始要求**：例如门禁引用“事件七要素”时，要确认运行时注入内容有明确对应关系。

**当前设计**：

- 每个关键时机的上下文契约；
- 消息顺序、来源、注入方、注入时机和可见性；
- 概念引用绑定表；
- “知识库存在”与“运行时可见”严格区分；
- 未绑定概念引用设为一票否决。

**对应文件**：`06-prompt-architecture-method-v0.md`、`11-runtime-and-context-core-gates-v0.md`、`08-validation-model-v0.md`。

**结论**：已覆盖，并提升为硬门禁。

### 3. 是否详细介绍业务背景

**原始要求**：角色身份定义、语气与行为约束等。

**当前设计**：

- 业务与角色行为契约；
- 产品目标、服务对象、角色、目标优先级、不做什么、行为/安全边界、语气、异常和信息不足行为；
- 卡片显式“非最终/旧项目”限制不能被忽略。

**对应文件**：`03-input-acquisition-model-v0.md`、`12-original-input-core-gates-v0.md`。

**结论**：已覆盖，并提升为核心门禁。

### 4. 是否明确每部分提示词的作用与职责，不重复、渐进式披露

**原始要求**：例如 MainAgent 不应看到和执行门禁判断有关的信息。

**当前设计**：

- 提示词架构清单；
- 提示词职责与信息可见性矩阵；
- system/task/reminder/anchor/动态上下文/tool schema 放置方法；
- 唯一主要归属；
- 无效重复与必要重新注入的区分；
- 整套系统与局部提示词按范围读取最小充分知识。

**对应文件**：`06-prompt-architecture-method-v0.md`、`12-original-input-core-gates-v0.md`。

**结论**：已覆盖，并提升为核心门禁。

### 5. 是否在关键位置引导模型关注业务任务约束

**原始要求**：如 Anchor 提示词设计。

**当前设计**：

- 关键约束与注意力安排；
- 约束影响、漂移风险、主要归属、注入位置、注入方、频率、重复理由和测试方式；
- Anchor/reminder 只有运行时支持且确有漂移风险时才创建；
- 长对话和复杂输入测试。

**对应文件**：`06-prompt-architecture-method-v0.md`、`12-original-input-core-gates-v0.md`、`08-validation-model-v0.md`。

**结论**：已覆盖，并提升为核心门禁。

### 6. 校验可疑知识错误

**原始要求**：对可疑知识错误进行检查。

**当前设计**：

- 知识库内容默认真实；
- 只扫描明显冲突、断链、版本/数量异常、工具/字段不一致、显式非最终内容、prompt 自行发明规则和产物漂移；
- 形成知识疑点与冲突报告；
- 关键问题进入补全分支，非关键疑点不扩大阻塞范围。

**对应文件**：`03-input-acquisition-model-v0.md`、`05-zettel-kdb-shape-and-skill-implications-v0.md`、`12-original-input-core-gates-v0.md`。

**结论**：已覆盖，并提升为核心门禁。

### 7. 整理一个 Skill，规范提示词生产过程

**当前设计**：

- 八阶段生产工作流；
- 每阶段产物、门禁和暂停恢复；
- 三个人工确认点；
- 分支与突发需求处理；
- prompts 与 evals 逐单元同步生成；
- 静态校验、外部评测交接和结果诊断。

**对应文件**：`07-phased-production-workflow-v0.md`、`08-validation-model-v0.md`、`09-external-evaluation-handoff-v0.md`。

**结论**：已覆盖。

## 二、用户后续明确补充倒查

| 用户补充 | 当前设计 | 结论 |
|---|---|---|
| 从原始输入分析，不把可推导内容变成偏好问题 | 原始输入追溯表 + 需求事实/Skill 建议分层 | 已覆盖 |
| Skill 生成提示词，不是直接写当前项目提示词 | 通用方法与资金安全案例分离 | 已覆盖 |
| 人员可能知道要哪些提示词，也可能只知道目标 | 明确清单、目标驱动发现、变化驱动更新三种入口；Skill 可从知识库推导清单 | 已覆盖 |
| Skill 在类似项目知识库中运行 | 知识库优先运行模型 | 已覆盖 |
| 话题优先寻找知识 | 话题 → 根卡/原子卡 → 搜索补漏 | 已覆盖 |
| 入库内容默认真实，明显错误才提出 | 定向疑点扫描，不做无差别事实审计 | 已覆盖 |
| 缺失内容传给前台人员，通过人员/前后端 Agent 补全 | 知识补全协议 + 回写后重新检索 | 已覆盖 |
| 关键资料缺失不生成 | 输入就绪硬门禁 | 已覆盖 |
| 不一步生成，要分阶段稳定产出 | 八阶段 + 每阶段门禁和产物 | 已覆盖 |
| 突发需求后回归主线 | 中断分类、分支和检查点恢复 | 已覆盖 |
| Skill 只生成 prompts/evals，外部执行评测 | 外部评测交接、状态区分和结果诊断 | 已覆盖 |
| 需要考虑代码层 | 运行时集成契约；代码实现交给代码侧 Agent | 已覆盖 |

## 三、当前是否足够

### 足够进入正式 Skill 编写

已经具备：

- 清晰触发场景；
- 明确工作对象和责任终点；
- 输入来源和知识库运行方式；
- 核心产物与硬门禁；
- 分阶段流程；
- 暂停恢复和人工确认；
- prompt/eval 生成与外部评测职责；
- 真实案例验证；
- 代码层交接边界。

继续增加流程分析的边际价值已经下降。下一步应通过正式 Skill 编写和场景演练发现问题，而不是继续无限扩写设计稿。

## 四、建议增加的增强项（不是原始需求）

以下内容值得加入正式 Skill，但必须标记为方法增强，不能冒充原始输入。

### 建议 A：更新模式与影响分析

当前设计已提到漂移，但可以在 Skill 中明确两种入口：

- 新建模式：从任务清单生成新 prompts/evals；
- 更新模式：知识卡、需求、工具 schema 或代码契约变化后，先生成影响报告，再只更新受影响产物。

影响报告至少说明：变化来源、受影响 prompt、受影响 eval、是否需要重跑外部评测、未受影响范围。

**建议级别**：应纳入 V1。真实项目更常见的不是永远从零生成，而是持续更新。

### 建议 B：指令与数据的信任边界

除“消息是否可见”外，再明确：

- 哪些内容是系统指令；
- 哪些是项目知识；
- 哪些是用户数据；
- 哪些是工具返回或外部不可信内容；
- 冲突时遵循什么优先级；
- 如何防止用户数据或检索内容被误当成指令。

**建议级别**：应纳入 V1，作为运行时环境与上下文契约的一部分，而不是独立扩大成安全 Skill。

### 建议 C：上下文预算与重复成本

渐进式披露不能只靠主观判断。可在架构阶段记录：

- 每层大致内容规模；
- 重复规则的数量和理由；
- 长对话中动态上下文增长方式；
- 哪些细节可移出主 prompt 或改为条件注入。

不必在 V1 做精确 token 优化，但应保留上下文预算检查位置。

**建议级别**：建议纳入 V1 的轻量检查，精确优化留给后续版本。

### 建议 D：安全的更新与交付

更新现有 prompts/evals 时：

- 先生成差异和影响说明；
- 不静默覆盖已经在用的文件；
- 保留版本对应和回退位置；
- 明确哪些外部评测需要重新执行。

**建议级别**：纳入更新模式，不必单独增加生产阶段。

## 五、不建议继续扩张的内容

- 不把 Skill 扩张成后端代码实现 Skill；
- 不把它扩张成通用知识库维护 Skill；
- 不让它负责实际执行所有模型评测；
- 不内置资金安全顾问业务规则；
- 不在 V1 建立复杂的自动部署、CI 或线上监控系统。

这些能力可以通过交接契约与其他 Agent/Skill 协作完成。

## 六、就绪结论

正式 Skill V1 的建议范围：

1. 原始输入六项核心门禁；
2. 用户补充的需求清单、知识库优先、关键缺口阻塞、阶段化生产和外部评测交接；
3. 运行时集成契约；
4. 更新模式、指令/数据信任边界、轻量上下文预算和安全差异交付四项增强。

该范围已经足够完整，同时仍能保持 Skill 主体聚焦于“从项目知识库稳定生产系统 Agent prompts 与 evals”。
