> 日期:2026-08-13

> 依据:34 号 + 审查(4.4/5,核心缺口=缺工具权限层)+ 用户确认的 Agent 定义 **Agent = 提示词 + 执行策略 + 工具及其范畴**。

## 一、按 Agent 三部分定义重组为三层

当前结构只显式做了"提示词层"和(散在 SKILL.md 的)"执行策略层",**第三层"工具及权限范畴"缺失**。三层各有独立载体:

| 层 | 定义内容 | 载体(目标结构) |
| --- | --- | --- |
| **提示词层** | 七项共同原则;各任务目标/职责/禁止;证据不足表达;不静默选边;元信息意义与生命周期 | `shared/core-principles.md` + 各 `skills/<task>/SKILL.md` 的"目标/职责/禁止/七项映射"节 |
| **执行策略层** | 各任务如何运行:输入/步骤/阻断条件/状态/产物/完成条件/分支与回归点;**哪些步骤由提示词判断、哪些程序化校验** | 各 `skills/<task>/SKILL.md` 的"主流程/状态/产物"节(策略复杂时可拆 `strategy.md`) |
| **工具及权限范畴层**(新增) | 每个任务能用哪些工具、访问哪些目录/仓库、读还是写、何时需用户授权、能否调其他 Agent、**即使工具可用也不允许做什么** | **`shared/tool-permissions.md`**(权限矩阵 + 外部边界协议 + 禁止清单);各 SKILL.md 引用并声明本任务权限行 |

工具权限层独立成文、被所有 skill 经 `_shared/` 引用,使外部边界从"语义提醒"升级为"可执行权限协议"。

## 二、修正 ① 工具与权限矩阵(新增层,5 分)

### 权限矩阵

| 任务 | 知识库 | Prompt 文件 | Eval | 后端仓库 | 项目代码 | 写知识库 | 其他仓库 / 调其他 Agent |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Prompt Creation | 读 | 写 | 不访问 | 默认禁止 | 禁止修改 | 否(人员/knowledge-zettel) | 禁止 |
| Agent Eval Creation | 读(独立,不读 Prompt 作知识源) | 不作为知识源 | 写 | 默认禁止 | 禁止修改 | 否 | 禁止 |
| Prompt Inspection | 读 | 读 | 仅用户显式范围读 | 默认禁止 | 禁止修改 | 否 | 禁止 |
| Prompt Revision | 读 | 授权范围内写 | 不修改 | 默认禁止 | 禁止修改 | 否 | 禁止 |
| Runtime Integration Validation | 读 | 读 | 默认不访问 | **明确授权后只读** | 默认只读核验、不修改 | 否 | 禁止 |

### 权限协议要点

- **外部仓库访问四条件**(任意 task 访问非当前项目 KB 的外部仓库时必须齐备):用户主动明确要求 + 提供仓库地址 + 说明目的与范围 + 仅在授权范围定向只读。
- **授权记录**:每次外部访问记录仓库、目的、范围、只读确认。
- **即使工具可用也不允许**(明示禁止清单):
  - 不擅自访问未授权仓库/目录(即便技术上可读);
  - 不把对话中的临时答复当作 KB 已更新;
  - 不自动删除 Prompt 元信息;
  - 不静默选择 KB 或代码任一方(差异先归因);
  - 不自动跨流程修改 Eval(Prompt Revision 尤其);
  - 不自行修改后端代码(Runtime Validation 只报告);
  - 不默认扫描全库、不默认读取范围外 Eval。
- **KB 缺运行时信息时**(普通 Creation/Inspection/Revision):标记缺失 + 说明影响的 Prompt/规则/结论 + 生成可转交后端/前端 Agent 的信息请求 + 不自行访问后端 + 等人员补入 KB 后重新检索。

## 三、修正 ② "代码证明实际 / KB 证明预期 / 差异归因"(替换"以代码为准",5 分)

**34 号原表述**(过度):"工具契约/概念载体/注入时机/加载范围以代码为准;KB 可能过时。"——易被读成"代码事实自动获胜",与"不静默选边"冲突。

**改为**:

> 代码、Schema、日志是**"当前实际实现"的权威证据**;知识库是**"预期业务与设计"的权威依据**。二者不一致时**先归因**(Prompt 误写 / KB 过时 / 后端偏差 / 无法判断),**不自动以任何一方覆盖另一方**。
>
> - 代码能证明"当前实际值"(如工具参数名是 `event` 而非 `new_data`)。
> - 代码**不能决定**"产品应否这样设计"(如业务策略、角色定位、语气)。
> - 是修 Prompt、修 KB 还是修代码,**由项目人员裁定**(归因报告支撑,不自行执行)。

## 四、修正 ③ 禁止用职责声明"对冲"system 冲突(5 分)

**34 号原表述**(C 类建议):"任务 Prompt 声明唯一任务……对冲共享底座泄漏。"——"对冲"不可靠,下层 task 不应负责抵消上层 system 的冲突或污染。

**拆成两条,级别不同**:

- ✅ **职责声明(保留,C 类建议)**:任务 Prompt 正文声明"唯一任务/不做其他任务/不生成用户回复/只走专属工具",用于**提高局部任务清晰度**。
- 🚫 **禁止对冲(升级为 B 类必改)**:**不得**用职责声明"对冲/抵消"system 与 task 的冲突,或把 system 信息污染降级为可接受。system 与 task 冲突(如 system 说"不负责门禁"、task 要求执行门禁;或 system 为 cache 整段注入致门禁看见回复规则)**必须修复架构或装配**(迁出规则到正确载体/改装配顺序/拆分共享底座/换加载策略),不得因 task 写了"唯一任务"就放行。

层4 硬核对的判定随之收紧:发现 system/task 冲突或真实装配泄漏 → **fail/架构阻塞**,职责声明不作为减免理由。

## 五、修正 ④ 验证通过 vs 人工删元信息分成两个状态(4 分)

**34 号原表述**(混淆):"`final-ready` 须同时满足交付状态通过 + 生命周期达 `final-runtime-prompt`(元信息已人工删除)+ 后端校验通过。"——把"内容/集成验证通过"和"人工定稿清理完成"混为一个状态。

**改为分阶段**(状态名不堆多):

```text
validation-passed  (知识/运行时/静态/行为验证完成,具备人工定稿条件;元信息仍在)
  → 等待人员定稿
  → 人员手动删除元信息
  → final-runtime-prompt  (人工清理后的运行稿)
```

- `validation-passed`:验证完成、可定稿(元信息保留,因定稿/追溯/回验仍需它)。
- `final-runtime-prompt`:人员手动删元信息后的运行正文(上线用)。
- `final-ready` 若保留,语义 = `validation-passed`(验证完成、具备定稿条件),**不要求元信息已删**。
- 元信息删除是**独立的定稿动作**,不与质量验证状态耦合。
- 生命周期与质量状态**只在确实需要程序判断时并存**;首次 Runtime Validation 执行后再决定是否需要机器可识别的四态(见 §八)。

## 六、第五 Skill `runtime-integration-validation` 七项映射(草案)

证明七项是共同宪法(不只 KB 任务用):

| 七项 | Runtime Validation 检查什么 |
| --- | --- |
| 需求先行 | 用户授权的仓库、目的、范围、被核验的 Prompt 生产稿 |
| 运行环境 | 真实消息装配顺序、工具 schema/参数/枚举/返回、输出消费、异常路径 |
| 上下文绑定 | Prompt 预期概念与真实注入消息/字段的对应 |
| 业务背景 | **仅核对代码是否承载已确认的业务要求,不重新决定业务知识** |
| 职责与渐进披露 | 每个 Agent 实际收到的信息是否符合预期职责;共享底座是否泄漏无关规则 |
| 关键约束位置 | Anchor/reminder 是否真有运行时钩子、加载时机是否如声明 |
| 知识错误 | 发现 KB 预期与代码事实差异并归因(四类),不静默选边 |

## 七、后端校验范围澄清(避免吞并 Inspection,3 分)

Runtime Validation **只核验 KB 中可与实现对应的部分**:文件名、装配位置、工具、消息、字段、输出消费、异常路径、加载时机、跨层冲突。

它**不重新判断**:角色定位是否正确、业务策略是否合理、语气是否符合用户、产品决策是否正确——这些归 Inspection(KB 视角)与人员。否则 Runtime Validation 会吞并 Inspection 职责。

## 八、元信息生命周期:原则保留,四态先验证

- 元信息生命周期**原则**(5 分,必须保留):生产/审查/修订/后端校验期保留;定稿由人员手动删;Skill 不擅删;"HTML 注释进入模型"是实验输入状态变量,不是生产阶段错误;删前确保追溯信息在清单/版本记录中保留。
- **四态机器状态机**(3 分,先验证再定):暂作生产约定(生产稿→后端校验候选→验证通过待定稿→人工清理运行稿),不急状态机;首次 Runtime Validation 实际执行后再决定是否需要四个机器可识别状态。
