## 三、问题初步归类

### 基本成立，优先讨论

1. **P1：inspection 缺少独立子协议**  
   当前八阶段和三确认点主要为生产设计，导致执行者自行跳阶段和改写含义。

2. **P2：manifest 校验脚本与已有草稿审验不匹配**  
   应明确适用边界，或提供不依赖 manifest 的轻量检查模式。

3. **P5：两个“入口模式”术语混淆**  
   任务类型与 prompt 清单获取方式应使用不同名称。

### 问题存在，但报告建议不能直接采用

4. **P3：派生综述与原始知识源**  
   真问题是没有先确认项目知识库契约和权威来源层级。不能通用地规定“所有派生综述都不可信”；某些项目可能明确把经过审核的综述设为权威入口。应遵循项目契约：权威正文、导航材料、派生文本、草稿分别是什么。本项目已经明确 Zettel_KDB 的权威来源，因此执行者优先读取背景综述属于偏离已有约定。

5. **P4：三份 reference 未读取**  
   当前 SKILL.md 已写明在检索知识时读取 `knowledge-discovery-and-gaps.md`，执行者没有遵守，不能简单归因为 reference 设计无效。但“按需”表述确实可能不够强，需要判断是加强必读路由，还是把极少数硬规则内联，避免重复和上下文浪费。

## 四、与两个暂存任务的关系

### 对暂存项 19：inspection 范围与归因

报告证明该问题成立，而且比 P1 更深：

- 本次实际检查了现有 prompts 的六项门禁和静态组合；

- 这与用户提出的“检验还应验证 prompt 生产范围和清单完整性”存在冲突，必须由我们重新设计，不能直接采用报告结论。

### 对暂存项 20：知识缺口补全产物

本次发现知识冲突后，只把它写成检验发现，没有生成可执行的知识补全请求。因此：

- 当前机制在 inspection 中是否应同步产出补全任务，尚未定义；
- 现有补全模板是否足够，仍未被真实验证；
- 这项暂存审验继续保留。

## 五、建议的后续讨论顺序

1. 先定义 inspection 的目标和范围：是否必须验证 prompt 清单本身；
2. 再定义 inspection 遇到知识缺口时，是只报告还是同时生成补全任务；
3. 据此设计 inspection 独立子协议、确认点、交付物和状态；
4. 再处理脚本轻量模式、知识源契约和 reference 必读路由；
5. 修改后用同一项目重跑回归；
6. 之后分别演练生产和 eval-only 模式。
