## 一、知识库的结构契约

该知识库不是普通 Markdown 文档集合，而是 Zettelkasten 风格的项目知识网络：

- 每张卡一个文件夹，文件夹名、标题和唯一地址一致；
- `page.html` 是权威制品，`text.md` 是派生文本；
- 每张卡只声明一个认识论类别；
- 卡片强调原子性，一张卡应能被独立引用；
- 内部链接与反向链接形成知识关系；
- `index.html` 只收录高价值节点，不是全量目录；
- `search_index/index.json` 提供全量搜索字段；
- `topics_index/topics.json` 用话题聚合跨卡片知识。

## 二、认识论类别对 Skill 的意义

契约提供六类知识位置：

- `idea / flash`：未验证想法；
- `record / rewind`：已经存在或发生过，但不担保真假；
- `truth / reality`：已确证、有据事实；
- `decide / closure`：信息不全时做出的决定；
- `conclusion / rooting`：综合多张卡形成的新认识；
- `anecdote / unfollowed`：有情节但未跟进的故事。

用户补充了项目的实际使用约定：**进入项目知识库的内容一般默认真实、可用于提示词生产，除非 Skill 发现明显错误。**

因此，认识论类别用于理解卡片性质和使用方式，不作为逐条重新取证的门槛：

- `record` 在此类项目知识库中默认可作为项目事实使用；
- `decide` 表示项目已经选择的做法，生成时保留其适用范围；
- `conclusion` 适合作为主题骨架和知识入口；
- 卡片自身若明确写有“非最终”“待确认”“来自旧项目”等限制，仍必须保留；
- `idea` 和 `anecdote` 若出现，应结合卡片自身措辞判断，不能自动提升为确定规则。

只有出现明显错误信号时才发起校验，例如同一概念互相矛盾、引用目标不存在、工具字段前后不一致、版本明显异常，或内容与卡片自身限定冲突。

## 四、Skill 在此类知识库中的推荐读取顺序

### 1. 读取知识库契约

先读 `index-spec.md`，了解：

- 权威制品是哪一个；
- 合法类别及其含义；
- 原子性与链接规则；
- 索引是全量还是精选。

不同项目的类似知识库可能有不同契约，Skill 不能写死本项目的六类名称。

### 2. 定位本次提示词任务

从用户任务、任务卡、话题索引或搜索索引确定：

- 要生成整套系统提示词还是局部提示词；
- 对应哪些 Agent、节点或执行时机；
- 预期产物和验收范围。

### 3. 话题优先发现相关知识

- 先用 `topics_index` 匹配与任务相关的话题，快速取得主题全景和相关卡组；
- 再沿话题中的根卡、综合卡和引用读取原子卡；
- 再用 `search_index` 按标题、摘要、关键词和更新时间补找遗漏；
- `index.html` 可辅助寻找高价值节点，但不能用它判断知识是否完整。

### 4. 从综合卡进入原子卡

先读 `conclusion / rooting` 类型的体系总览，再沿引用进入产品定义、工具、流程、角色、约束和评测等原子卡，避免只读一张综合摘要就生成提示词。

### 5. 核验权威内容与引用

- 搜索和初读可以使用 `text.md`；
- 进入正式提示词的关键规则应回看契约指定的权威制品 `page.html`；
- 检查引用是否链接到真实存在的卡；
- 对未链接的来源文字，不能假设知识库中存在对应证据；
- 对照 `revised`、适用版本和知识类别判断是否可用。

### 6. 建立任务覆盖图

把本次提示词生产需要的五类输入映射到具体卡片：

- 目标与交付契约；
- 运行时事实；
- 系统关系与继承边界；
- 业务语义与关键约束；
- 证据与验收依据。

存在空白、明显错误、来源冲突或卡片无法独立解释时，登记为知识缺口。卡片类别本身不构成缺口。

## 五、当前观察到的风险信号

以下只是本次只读检查发现的信号，不等同于已完成知识库质量审计：

1. 《项目背景说明.md》写“共 26 张卡片”，当前 `search_index/index.json` 为 25 张；可能存在统计口径或索引同步差异，需要核实。
2. 当前没有 `truth / reality` 卡；按项目“入库内容默认真实”的约定，这不构成提示词生产阻塞项。
3. `page.html` 是权威制品、`text.md` 是派生文本；Skill 若只读取 Markdown，可能错过权威版本或同步差异。
4. 某些卡片引用“产品实现约定”等文字来源，但未形成可点击的内部卡片链接；这类来源需要进一步定位，不能视为已具备可追溯证据。
5. 已知知识库中存在两套回复阶段“四步流程”描述；综合卡和主题聚合不能自动消除语义冲突。
6. 当前提示词卡主要描述提示词的作用、规则和文件位置，未包含逐字提示词原文。这说明“提示词设计知识”与“正式提示词内容”目前可能分属不同存储位置。

## 六、对 Skill 设计的直接要求

Skill 需要具备以下知识库原生能力：

- 先读取知识库契约，再决定检索和引用方式；
- 通过话题、搜索、根卡和引用网络逐层取证；
- 默认信任已进入项目知识库的内容，用认识论类别理解其性质和适用方式；
- 不做无差别事实复核，只检查明显错误、冲突、断链、版本异常和卡片显式限定；
- 区分权威制品与派生文本；
- 检查任务覆盖、断链、未定义术语、版本差异和冲突；
- 对生成规则保留卡片级来源追溯，用于维护和更新，不要求用户重新证明每张卡；
- 关键缺口存在时生成知识补全请求，不生成提示词；
- 补全知识回写后重新检索，不依赖临时对话记忆；
- 生成提示词时保留“哪条规则来自哪张卡”的映射，供后续校验和更新。

## 七、同项目中已经存在的产物分工

继续检查知识库同级目录后，已有分工可以直接确认，无需让用户重复回答：

- `Zettel_KDB/`：项目知识来源；提示词从这里推导生成。
- `prompts/`：正式提示词目录，目前包含 9 个文件、5 层；README 明确写明“从 `Zettel_KDB/` 知识库推导生成”，每个文件顶部标注来源卡片。
- `evals/`：与 prompts 镜像的 rubric 和 judge prompt；与提示词同源，都从知识库抽取，提示词变化时同步更新。

因此，适用于类似知识库的 Skill 应采用“知识源与生成制品分离”的默认模型：

1. 项目知识库是提示词规则、业务知识和系统事实的来源；
2. 正式可执行提示词写入项目约定的 prompts 产物区；
3. 评测材料写入与 prompts 对应的 evals 产物区；
4. prompts 和 evals 都保留到知识卡的来源映射；
5. 知识缺口先补知识库，再重新生成或更新 prompts 与 evals；
6. 具体目录名不能在通用 Skill 中写死，应从项目契约、任务说明或现有结构中发现。

## 八、仍需后续设计的问题

- 如何把一组原子知识卡转换成系统级提示词架构，而不是简单拼接卡片内容；
- 如何在每个 prompt 文件中表达可维护的来源追溯；
- 如何检测知识库、prompts 和 evals 是否发生漂移；
- 类似知识库没有现成 prompts/evals 目录约定时，Skill 应如何产出目录建议并等待确认。
