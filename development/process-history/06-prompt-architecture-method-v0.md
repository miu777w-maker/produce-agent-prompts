# 系统 Agent 提示词架构方法 V0

> 主线步骤 3 产物。  
> 目标：把知识库中的原子知识转换成提示词架构，而不是把卡片内容简单拼接成一篇长 prompt。

## 一、承接需求中的“提示词生产任务清单”

架构设计不能脱离需求重新决定要写什么。进入本步骤时，应先取得输入获取阶段形成的任务清单，包括：

- 需求明确要求的提示词及其职责；
- 已指定的文件、层级、配对和加载时机；
- 本次新建、重写或更新的范围；
- 需求没有说明的关键缺口；
- Skill 基于系统运行分析提出、但尚未成为需求的候选调整。

架构设计负责验证这些提示词与真实执行环境是否匹配，并补足实现所需信息；不把 Skill 自己的架构推断冒充原始需求。

## 二、先形成“提示词架构清单”，再写正文

Skill 通过话题和卡片取得知识后，第一项架构产物不是提示词正文，而是一份提示词架构清单。每个目标文件或运行时提示片段至少记录：

- 名称与产物路径；
- 对应的 Agent、任务或执行单元；
- 触发时机；
- 该次执行叠加的其他提示词；
- 实际可见的系统消息、用户消息、状态、知识和工具；
- 唯一职责；
- 必须输出的内容或工具调用；
- 上游输入与下游消费者；
- 失败、拒绝和信息不足路径；
- 来源知识卡；
- 对应 eval/rubric；
- 明确不应承载的内容。

该清单回答“需要哪些提示词、为什么需要、何时加载、各自负责什么”。清单不成立时，不进入逐字编写。

## 三、为每个关键执行时机还原上下文快照

原始输入特别强调：不能在提示词里引用执行时并不存在的概念或“代词”。因此 Skill 要针对每个执行时机建立上下文快照：

| 上下文部分 | 需要确认的问题 |
|---|---|
| 底座提示词 | 本次实际继承哪些系统级规则？ |
| 任务提示词 | 当前任务独有的目标、规则和边界是什么？ |
| reminder / anchor | 是否会注入？在什么时机、以什么消息角色注入？ |
| 用户输入 | 原文如何包裹、清洗或结构化？ |
| 对话历史 | 是否存在、截取范围如何、是否包含其他事件？ |
| 运行时状态 | 哪些字段会注入，字段名和语义是什么？ |
| 领域概念 | 提示词引用的术语定义是否在本次上下文中实际可见？ |
| 工具 | 模型能看到哪些工具及 schema？哪些工具明确不可用？ |
| 输出通道 | 自然语言、结构化输出、工具调用或多者组合？ |

### 引用成立规则

提示词中出现“上述规则”“当前事件”“七要素”“按门禁标准判断”等表达时，Skill 必须能够指向本次上下文中的明确内容：

- 已在当前提示词中定义；或
- 位于本次真实叠加的底座提示词中；或
- 由运行时以明确字段或消息注入；或
- 由可见工具 schema 明确定义。

如果只能在知识库中找到定义，但运行时上下文没有注入，则引用不成立。知识库是生成依据，不等于模型运行时自动可见。

## 四、规则放置方法

每条从知识卡提取出的规则先判断作用域，再决定放置位置。

### 1. 系统底座

适合放：

- 所有目标执行单元都需要遵守的基础行为；
- 通用消息解释方式；
- 全局工具纪律；
- 所有任务共有的安全或表达底线。

不适合放：

- 单一门禁的判定条件；
- 某一业务任务的状态机；
- 只有局部工具才使用的具体流程。

### 2. 任务主提示词

适合放：

- 当前执行单元的目标；
- 当前任务的领域定义、判定规则、步骤和边界；
- 当前任务可用工具的使用方式；
- 当前任务的输出契约和异常处理。

任务提示词要能在其真实上下文中独立执行，但不重复已经通过底座稳定提供、且当前一定可见的内容。

### 3. reminder / anchor

只有同时满足以下条件时才考虑单独设置：

- 约束对当前任务成败或安全结果非常关键；
- 长上下文、循环、工具调用或多轮对话中容易漂移；
- 运行时确实支持在关键时机再次注入；
- 重复带来的注意力收益高于上下文成本。

reminder/anchor 不复制整份主提示词，只重申最容易丢失的判定轴、边界或强制动作。

### 4. 运行时动态上下文

用户输入、对话历史、事件状态、页面状态、当前工具结果等动态信息，不写死在静态提示词中。提示词只说明：

- 这些数据以什么明确标识出现；
- 各字段代表什么；
- 如何使用、不能如何使用；
- 缺失、矛盾或异常时怎么办。

### 5. 工具 schema 与提示词

工具参数、枚举和返回结构应以实际 schema 为准。提示词负责解释调用时机、业务取向和结果用途，不应复制一份可能与 schema 漂移的完整接口定义；只有模型执行所必需且运行时不会自动展示的部分才进入 prompt。

## 五、职责唯一归属与必要重复

“不重复浪费”不等于任何内容只能出现一次。Skill 需要区分：

### 无效重复

- 同一次执行中，底座已经完整提供某规则，任务提示词又无理由复制；
- 多个并行任务各自携带与自身无关的业务知识；
- 工具 schema 已自动可见，prompt 又复制整份字段定义并可能漂移。

### 有目的的重复

- reminder/anchor 在新的关键时机重新注入高风险规则；
- 局部提示词无法保证继承某底座内容，必须自包含必要定义；
- 一个概念需要在不同执行单元中使用，但各自只获得与职责相关的最小定义。

每次重复都必须说明：重复发生在哪两个运行时位置、为何模型在第二个位置仍需要看到、如果删除会产生什么风险。

## 六、渐进式披露的三层应用

### 1. Skill 自身读取知识

先按话题读取相关卡组，再按提示词任务补充引用和搜索结果，不无差别加载整个知识库。

### 2. 提示词文件分层

全局规则、任务规则、注意力锚点、动态状态和工具 schema 分别由合适载体承担。

### 3. 单次运行上下文

每个执行单元只获得完成本职任务所需的信息。以资金安全顾问为例：门禁不需要回复阶段的四条路径；回复任务不需要其他门禁的详细判定过程，除非它确实会在运行时使用其结果。

## 七、知识卡到规则的转换记录

对每条进入提示词的关键规则记录：

| 字段 | 含义 |
|---|---|
| 来源卡 | 规则来自哪张知识卡 |
| 原始知识 | 卡片中的原意，不先改成 prompt 文案 |
| 目标执行单元 | 哪个 Agent/节点需要执行 |
| 放置位置 | system/task/reminder/anchor/动态上下文/工具 schema |
| 放置理由 | 为什么该位置在运行时有效 |
| 可见性证明 | 执行时如何确认模型真的能看到 |
| 验收映射 | 对应硬检查、rubric 或测试案例 |

这样可以防止“卡片内容看起来重要，所以到处复制”的拼接式生产。

## 八、资金安全顾问案例反向验证

当前项目已经展示出以下架构：

- `main_agent/system_prompt`：公共底座，只承载基础行为框架；
- `gate/fund_safety`：局部任务判定轴、边界、取向与工具输出；
- `gate/fund_safety_reminder`：在循环时重申判定轴、模糊放行取向和强制工具调用；
- `fund_security_advisor/task`：回复阶段的角色、事件处理流程、状态机、工具使用和输出边界；
- `fund_security_advisor/anchor`：每次执行重新注入信息确定性与服务范围约束。

该案例说明：规则的最终位置由“作用域 + 执行时机 + 漂移风险 + 实际注入能力”共同决定，而不是由知识卡标题直接决定。

同时也说明 Skill 必须检查重复是否有运行时理由。例如用户输入标签格式同时出现在底座和回复 task 中：仅凭文本重复无法直接判错，需要核对回复 task 是否始终继承该底座；如果始终继承且没有重新注入需要，可能是无效重复；否则可能是必要自包含。

## 九、步骤 3 的完成条件

- 已形成提示词架构清单；
- 已保留需求明确指定的提示词清单和职责，并区分需求事实与 Skill 建议；
- 每个执行时机有上下文快照；
- 每条关键规则有唯一主要归属；
- 所有跨层引用在真实上下文中成立；
- 每处重复都有运行时理由；
- 每个执行单元满足最小必要上下文；
- 每个提示词产物都能追溯到知识卡并映射到验收材料。
