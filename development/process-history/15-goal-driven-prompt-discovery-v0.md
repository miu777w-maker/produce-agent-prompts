# 目标驱动的提示词清单发现能力 V0

> 修正：人员不一定知道系统需要哪些提示词。Skill 必须能从项目目标和知识库中的系统知识推导提示词架构候选。

## 一、“需求先行”的正确含义

需求先行不等于“用户必须先列出 prompt 文件”。它只要求先明确：

- 想让哪个系统、Agent 或业务流程实现什么结果；
- 本次是新建、更新还是解决某个问题；
- 涉及的大致产品/系统范围；
- 有哪些明确不能改变的要求；
- 最终需要可执行 prompts、evals，还是还包括集成契约。

提示词清单和职责既可能由需求直接给出，也可能由 Skill 从知识库推导。

## 二、三种任务入口

### A. 明确提示词清单模式

人员已经给出提示词名称、职责或修改范围。Skill 保留原始清单，用知识库验证其与实际执行架构是否匹配；发现遗漏或职责冲突时提出建议，不静默改变明确要求。

### B. 目标驱动发现模式

人员只知道产品目标、Agent 能力或要解决的问题，不知道需要哪些提示词。Skill：

1. 通过话题定位相关产品、系统流程和实现知识；
2. 识别 Agent、任务节点和独立模型调用；
3. 还原关键执行时机及上下文；
4. 识别全局规则、局部规则、动态上下文、工具约束和漂移风险；
5. 推导需要哪些 system、task、reminder/anchor 或其他载体；
6. 为每个候选 prompt 给出职责、触发时机、必要性和不承载内容；
7. 形成建议的提示词生产任务清单；
8. 交给前台人员确认后再逐字生成。

### C. 变化驱动更新模式

入口是知识卡、工具 schema、系统流程或业务规则变化。Skill 识别受影响执行单元，追溯现有 prompts/evals，生成需要新增、修改、合并或删除的清单，经确认后只更新受影响产物。

## 三、如何从知识库推导提示词清单

### 1. 建立执行单元地图

识别哪些节点独立调用模型、哪些共享底座、哪些并行/串行/条件触发，以及各自不同的输入、工具、输出和失败路径。

### 2. 识别规则作用域

- 所有执行单元共有 → system 底座候选；
- 单一执行单元独有 → task 候选；
- 动态数据 → 运行时上下文，不生成静态 prompt；
- 关键且易漂移、运行时支持重注入 → reminder/anchor 候选；
- 确定性程序逻辑 → 优先放代码/schema，不强行转成 prompt。

### 3. 决定是否需要独立 prompt

只有满足至少一项才建议拆成独立 prompt：

- 独立执行时机；
- 独立职责和输出契约；
- 独立工具集合或 schema；
- 不同上下文可见范围；
- 需要在特定时机重新注入；
- 需要独立版本、评测或维护。

如果只是同一执行单元中的一个小节，不自动拆文件。

### 4. 形成候选清单

每个候选项说明：名称、类型、执行单元、加载时机、唯一职责、所需知识和工具、不承载内容、独立存在理由、对应 eval、置信度和待确认问题。

## 四、确认点调整

三个确认点统一改为：

1. **任务目标确认**：目标、范围和不可改变要求；如已有清单一并确认。
2. **提示词方案确认**：Skill 最终形成的生产清单、职责、架构、上下文与加载时机。
3. **最终交付确认**：prompts、evals、集成契约和校验状态。

## 五、关键阻塞

目标驱动模式下，如果知识库不足以还原执行单元、关键上下文、工具/输出契约、业务边界或继承关系，Skill 不能凭常识设计提示词清单；此时生成知识补全请求。

## 六、资金安全顾问示例

即使人员只说“为资金安全顾问生成系统提示词”，Skill 也可从知识库发现共享 MainAgent、三个独立门禁、门禁循环提醒、回复任务和长对话 anchor，从而推导 9 个 prompt 文件候选，再由前台人员确认。
