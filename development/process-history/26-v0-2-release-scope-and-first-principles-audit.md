# V0.2 发布范围与第一性原理审视

> 日期：2026-08-12  
> 目标：在用户正式进入知识库 Creation 前，确定本版本必须修什么、延后什么、哪些能力已验证。

## 一、第一性目标

Skill 的根本目标是：从项目权威知识与真实运行条件出发，稳定地产出或审验可执行、可追溯、可评测的 Agent prompts；证据不足时不制造虚假确定性。

更新项只在满足以下条件时进入 V0.2：

1. 不修会影响正确结论、流程授权或版本可用性；
2. 已被真实执行暴露，或是下一步 Creation 的必经条件；
3. 现有规则不能稳定覆盖，而非执行者单次没有遵守；
4. 稳定性收益大于新增上下文和流程成本。

## 二、当前能力的实际验证状态

| 流程/能力 | 状态 | 证据边界 |
| --- | --- | --- |
| Inspection 启动、范围确认、独立重建清单 | 已真实回归 | 两轮资金安全顾问整套审验，第二轮通过 |
| Inspection 六项门禁、静态组合、缺口补全 | 已真实回归 | 第二轮报告和唯一 transcript 已定位 |
| 运行时输入/工具供给证据约束 | 已真实回归 | 无代码时正确停在待核验并生成工程取证 |
| 正式包确定性校验脚本 | 最小合法包测试通过 | 未在真实项目 manifest 上运行 |
| Creation 目标驱动整套生产 | **未端到端调用** | 方法设计存在，下一步进入首次正式使用 |
| Creation 人员给定清单的局部生产 | **未调用** | 仅设计存在 |
| Revision | **未调用** | 仅设计存在 |
| Eval-only | **未调用** | 仅设计存在；Inspection 已审过现有 eval，但不等于 Eval-only 通过 |
| 外部评测回传到 final-ready | **未调用** | 只验证了克制状态，没有完成状态链 |
| 中断/分支恢复 | 部分设计验证 | 对话设计期使用过，尚未在正式 Creation 产物流程完整演练 |

## 三、V0.2 必须修改

### 5 分

- 新增 `inspection-blocked` 及门禁状态汇聚：避免“检查完成但待外部证据”被误写成未完成或失败。

### 4 分

- 集中增加六项门禁的 Inspection 判定映射；
- 集中运行时证据缺失的降级、分组、取证和状态规则；
- 增加已有 eval 的 Inspection 审查检查表；
- 明确八阶段主要属于 Creation，Revision 只复用受影响阶段；
- 在 `SKILL.md` 提升“整套 Inspection 必须独立重建应有清单”的硬规则。

### 低成本 3 分

- 允许范围确认前轻量 orient，不开始正文检索；
- 给四种流程提供可被项目契约覆盖的默认产物目录；
- 知识补全与运行时取证在需要交给不同责任方时形成独立 Markdown 文件。

## 四、本轮不加入

- 不新增第七项“输入供给”门禁：现有 Gate 1/2 与运行时契约已真实覆盖；
- 不新增一页式 reference：避免重复和新路由层；
- 不强制 transcript：只在 Skill 验证、争议或严格审计时记录；
- 不绑定 Claude/Codex 记忆系统；
- 不把全部模板标签化作为阻塞项；
- 不因 Creation 未测试而扩写大量假想规则。

## 五、V0.2 发布声明

- Inspection：完成第二轮真实回归，可用于正式审验；
- Creation：具备明确生产协议，可进入首次正式使用，但必须把本次执行视为 Creation 首轮验证，保存检查点和反馈；
- Revision、Eval-only：可使用但仍处于未端到端验证状态；
- 任何流程都不得在没有外部行为证据时声称最终可用。

## 六、首次正式 Creation 的观察项

1. 启动是否正确识别人员是否已有 prompt 清单；
2. 是否先确认目标、范围和不可改变要求；
3. 是否从知识库推导清单而非照抄现有草稿；
4. 是否在关键知识/运行时输入不足时停止生成并输出独立补全任务；
5. 第二确认点是否展示 prompt 清单、职责、上下文、加载时机和六项门禁，而非只给文件名；
6. 是否逐单元生成 prompt + eval 并保存来源映射；
7. 是否把动态数据、工具/schema 和 code 逻辑放到正确载体；
8. 是否完整落盘，不把正式文案只留在聊天；
9. 是否停在与证据相符的状态；
10. 中断或补全分支结束后是否回到正确主线。
