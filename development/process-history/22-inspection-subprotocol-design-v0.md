# Inspection 独立子协议设计 V0

> 日期：2026-08-11  
> 来源：暂存项 19 + Claude 首次真实执行反馈  
> 状态：讨论稿，尚未修改正式 Skill。

## 一、Inspection 的目标

Inspection 不是“检查现有 prompt 文案”，而是判断当前提示词体系是否足以、正确且真实地承载项目目标。

完整检验应回答四组问题：

1. **生产范围是否正确**：这次应该覆盖哪些系统、Agent、模型调用和关键时机；
2. **prompt 清单是否正确**：应该有哪些 prompts，现有清单是否缺失、多余、错误拆分、错误合并或职责错位；
3. **prompt 内容与组合是否正确**：每份 prompt 及其运行时组合是否满足六项核心门禁；
4. **问题从哪里产生**：是需求、知识、架构、生成、运行时还是 eval 的问题。

如果只完成第 3 组，报告必须命名为“现有 prompt 内容审校”，不能声称“整套系统提示词检验完成”。

Inspection 的最终目的不是形成一份漂亮报告，而是为后续独立的修改/优化流程提供足够证据，使提示词体系最终能够形成可用版本。Inspection 本身不执行修改。

## 二、三种检验范围

### A. 单 prompt 检验

检查当前 prompt 的必要性、唯一职责、直接上下游、知识忠实度、运行时真实性和对应 eval。默认不重建全系统，但若发现职责无法定位或依赖不明，扩大到直接相关执行单元。

### B. 局部组合检验

检查一个任务链、一个 Agent 或若干相互加载的 prompts。重建该局部范围内应有的执行单元和 prompt 清单，并检查上下游和组合上下文。

### C. 整套系统检验

必须独立重建系统执行单元、规则作用域和应有 prompt 清单，再与现有 prompts/evals 对比。不能把现有文件列表当作正确范围的前提。

## 三、启动确认

Inspection 只需要一个常规启动确认点：

- 检验范围：单 prompt、局部组合或整套系统；
- 当前目标：只报告，还是报告后另行决定是否修复；
- 权威知识库、运行时事实来源和现有 prompts/evals 位置。

默认只报告、不修改。用户请求本身已经明确时不重复提问。

## 四、推荐的七步检验流程

### I1. 冻结检验对象与证据契约

记录项目目标、检验范围、不可改变要求、权威知识源、派生导航材料、运行时/代码事实来源、现有 prompts/evals 和版本。

不要通用地假设原始卡一定优于综述；先遵循项目知识契约。派生材料只有在项目明确赋予权威性时才作为事实源，否则仅作导航并追溯其引用。

### I2. 从知识与运行时重建“应有体系”

在不把现有 prompt 清单当成正确答案的前提下：

- 还原目标系统和模型执行单元；
- 还原关键执行时机、消息、变量、状态、工具、输出和异常；
- 判断规则是全局、局部、动态、重注入、工具/schema、code/parser 还是 eval；
- 推导本范围内应有 prompt 清单、职责、加载时机和不承载内容。

可以读取现有 prompts 了解实现，但最终“应有清单”的证据必须来自目标、知识和运行时事实，不能循环证明。

### I3. 对比应有清单与现有清单

逐项分类：

- `matched`：必要且职责/时机匹配；
- `missing`：应有但未生成；
- `extra`：现有但没有独立必要性；
- `wrong-split`：本应合并却被无理由拆分；
- `wrong-merge`：职责/时机不同却被合并；
- `mis-scoped`：prompt 存在，但作用范围或可见信息错误；
- `uncertain`：知识或运行时证据不足，不能判断。

该步骤先于逐字质量检查。若清单根基错误，后续仍可检查现有文件，但必须把结论限制为“对当前草稿的局部发现”。

体系或清单存在关键错误时，不要提前结束 inspection。继续审查现有 prompt 内容，并把发现分成：

- **上游派生问题**：主要由错误体系、职责或加载关系造成；
- **单元自身问题**：即使未来重构体系，该 prompt 中的知识误读、指令冲突、概念不明、工具/输出错误或表达问题仍需处理；
- **重构后需复验**：当前能观察到问题，但体系改变后结论可能变化。

这种继续审查的方法是否能稳定产生有效结论，需要在实际回归中验证；报告必须保留不确定性，不能假设错误体系下的每条文案结论都会在新体系中继续成立。

### I4. 对每个现有/应有单元执行六项门禁

把六项作为验收基线：运行环境、执行时机上下文与概念绑定、业务角色、职责与可见性、关键约束注意力、知识疑点与冲突。

同时检查需求忠实度、知识忠实度、运行时真实性、指令可执行性、表达和 eval 完整性。

### I5. 执行静态系统集成检查

按真实装配顺序重建上下文，检查跨层冲突、重复、动态字段、工具 schema、上下游、并行隔离、异常路径和 prompt/eval/version 对应。

没有 manifest 时，不运行正式包校验器；记录“尚未形成可机器校验的正式包”，再执行适合草稿的轻量确定性检查。

### I6. 对问题进行现象与原因双重分类

不要把“错误/疏漏”直接等同于原因。

#### 现象类型

- 错误：已有内容与证据冲突；
- 疏漏：应有内容或产物缺失；
- 多余：无必要或无用途的内容/文件；
- 冲突：多个来源或载体不能同时成立；
- 不可验证：证据不足，暂不能判定。

#### 原因归属

- 需求/范围：目标、边界或不可改变要求未明确；
- 知识：知识库缺失、错误、冲突、过期、断链或非最终；
- 架构/清单：执行单元、prompt 数量、拆分合并、职责或加载时机推导错误；
- prompt 生成：有充分上游依据，但生成时误读、遗漏、擅自新增或表达错误；
- 运行时/code/schema：prompt 假设与实际装配、变量、工具、parser 或异常机制不符；
- eval：评测缺失、错误、与 prompt 漂移或证据不足；
- 尚不能归因：需要补充证据。

每条发现记录现象、证据、原因归属、置信度、影响范围、建议动作和回退阶段。不能证明原因时，不强行归到 prompt 生成错误。

### I7. 交付检验报告与补全任务

检验报告至少包括：

1. 检验范围、对象、版本和证据边界；
2. 应有 prompt 体系；
3. 应有与现有清单差异；
4. 六项门禁结论；
5. 静态集成结论；
6. 按严重度排序的发现；
7. 现象与原因归因；
8. 无法判断项和对应知识补全请求；
9. 当前状态及允许/不允许声称的结论；
10. 后续选项：补知识、改架构、改 prompt、补 eval、核查运行时或进入外部评测。

完整报告必须写入独立 Markdown 文件，并在对话中只返回结论摘要、文件路径、状态和下一决策入口。不要把完整报告只输出在聊天中。报告文件名至少包含 inspection 范围或任务标识及版本/日期，避免覆盖历史报告。

Inspection 完成后停止。只有用户明确启动修改/优化任务时，才把报告作为输入进入另一个流程；不得在 inspection 中顺手改 prompts、evals 或知识库。

## 五、Inspection 中的知识缺口处理

生产模式遇关键知识缺口时停止生成。Inspection 不应因此停止整份报告：

- 对受影响结论标记 `uncertain` 或 `blocked-by-knowledge`；
- 继续检查不依赖该缺口的范围；
- 不把无法验证的部分判为通过；
- 同步生成可直接交给项目人员或前后端 Agent 的知识补全请求；
- 补全入库后，回到 I2 或最早受影响步骤重新检验。

因此，“继续完成检验报告”和“阻止不可靠的合格结论”可以同时成立。

## 六、Inspection 状态建议

Inspection 报告可使用：

- `inspection-incomplete`：证据或范围不足，尚未完成必要检查；
- `inspection-failed`：发现关键范围、知识、架构、prompt 或运行时问题；
- `inspection-static-passed`：范围、清单、六项门禁和静态集成通过；
- `awaiting-external-evaluation`：静态通过，等待行为评测；
- `external-failed` / `external-passed`：收到可追溯外部结果。

Inspection 本身不产生 `final-ready`；只有进入修复/生产交付流程并完成最终确认后才使用该状态。

## 七、必须读取的 Skill 资源

整套系统 inspection 至少读取：

- `knowledge-discovery-and-gaps.md`：确定权威知识、覆盖和疑点；
- `core-production-gates.md`：执行六项验收；
- `prompt-architecture-and-runtime.md`：独立重建应有清单和运行时契约；
- `validation-and-external-handoff.md`：单元与静态组合检查；
- `artifact-templates.md`：需要形成正式检验报告和补全请求时读取。

单 prompt 或局部检验可按范围缩减，但不得跳过知识、六项门禁和直接运行时契约。

## 八、与首次反馈的处理关系

- 吸收 P1：把 inspection 设为一等流程，不再跳用生产阶段；
- 吸收 P2：正式包校验和草稿轻量检查分开；
- 修正 P3：以项目知识契约判定权威性，不机械贬低所有派生综述；
- 处理 P4：为整套 inspection 明确必读 resources；
- 修正 P5：inspection 同样需要验证清单，但不是生产时的“清单推导模式”，而是独立重建后对比。

## 九、待确认的关键判断

已确认：整套系统 inspection 默认采用“先依据目标、知识库和运行时事实重建应有体系，再与现有 prompts 对比”的方法。这样成本高于单纯文案审校，但只有这种检验能够回答提示词生产范围和清单是否正确。

已确认：体系错误时仍继续检查现有 prompt 内容，但区分上游派生问题、单元自身问题和重构后需复验项；该方法进入实际实验。

已确认：完整 inspection 报告写入独立 Markdown 文件；inspection 不自动进入修改。
