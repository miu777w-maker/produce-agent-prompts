# 资金安全顾问案例全流程走查 V0

> 目的：用现有 `Zettel_KDB/`、`prompts/` 和 `evals/` 反向验证提示词生产 Skill 的阶段、门禁和分支是否可执行。  
> 限制：这是方法走查，不修改当前项目产物，也不把现有产物倒推为完整原始需求。

## 一、案例范围

当前项目已有的提示词体系：

- 1 个 MainAgent 系统底座；
- 3 个门禁层，每层主 prompt + reminder；
- 1 个回复层，task + anchor；
- 共 9 个 prompt 文件；
- 对应门禁、MainAgent、回复 task 和 anchor 的 eval/rubric/judge 文件。

本次用“从项目知识库生成上述系统提示词及配套 evals”作为走查任务。该表述来自当前 `prompts/README.md` 对既有结果的说明，不冒充项目最早的原始需求。

## 二、阶段 0：启动与恢复

### 可取得的信息

- 知识库契约：`Zettel_KDB/index-spec.md`；
- 话题索引：4 个话题；
- 全量搜索索引：25 张卡；
- 正式提示词目录：`prompts/`；
- 评测定义目录：`evals/`。

### 判断

运行环境、知识源和派生产物位置明确，可以进入需求解析。

## 三、阶段 1：需求解析

### 可重建的生产任务清单

| 提示词单元 | 文件 | 职责 |
|---|---|---|
| MainAgent 底座 | `main_agent/system_prompt.md` | 所有任务共有的基础行为框架 |
| 第一门禁 | `gate/input_safety_check.md` + reminder | 合规判定 |
| 第二门禁 | `gate/fund_safety.md` + reminder | 资金安全问题判定 |
| 第三门禁 | `gate/same_event_check.md` + reminder | 同一事件判定 |
| 回复任务 | `fund_security_advisor/task.md` + anchor | 事件信息处理与回复生成 |

### 发现的任务来源问题

当前可以从“提示词体系”知识卡和 `prompts/README.md` 重建清单，但没有在本次检查范围内找到最初的提示词生产需求原文。

### Skill 应如何处理

- 如果用户本轮已提供明确需求，则使用用户需求作为阶段 1 来源，不阻塞；
- 如果没有明确需求，只能从现有体系倒推，则把上述清单标为“知识库确认的现状”，请求前台人员确认是否就是本次交付范围；
- 不把当前已有 9 个文件自动当作未来所有更新任务的范围。

## 四、阶段 2：知识发现与覆盖检查

### 话题优先发现

- “资金安全顾问 · 产品背景”提供产品、用户、事件模型与角色知识；
- “资金安全顾问 · 顾问核心设计”提供事件处理、回复策略与安全边界；
- “LLM 调用实现细节”提供提示词体系、工具、消息包裹和门禁实现；
- “agent 评测体系”提供双轨评测和 rubric 抽取方法。

### 五类输入覆盖

| 输入类别 | 当前覆盖 |
|---|---|
| 目标与交付契约 | 提示词体系和 README 可重建现状；原始生产需求需由本轮任务提供或确认 |
| 运行时事实 | 门禁并行、MainAgent 叠加、消息包裹、event_context、工具和回复阶段已有卡片 |
| 系统关系与继承边界 | “顾问服务的提示词体系”“核心处理流程”“提示词对”可形成架构 |

## 五、阶段 2 发现的关键阻塞

### 阻塞 A：门禁工具调用语义冲突

知识库同时存在：

- “分析后强制调用专属工具传 verdict”；
- “仅在触发拒绝条件时调用 report_xxx 上报”。

当前 prompts 选择了“每次都调用，verdict false 表示拒绝”。这是一个生成时的设计取舍，但新 Skill 不能在知识冲突未解决时自行选边。

**影响**：三个门禁主 prompt、对应 reminder、rubric 的 V1/V2，以及后端消费逻辑。

**建议补全方**：后端 Agent 检查真实工具 schema、调用代码和通过路径；项目人员确认目标契约。

### 阻塞 B：角色定位明确标注非最终

知识卡说明角色资料来自上一个类似项目、非本项目最终定稿。当前回复 task 使用了该角色，同时保留注释。

**影响**：回复 task 的身份、目标优先级、服务范围；anchor 中的服务定位；部分 MainAgent 沟通风格。

**建议补全方**：项目人员给出本项目正式角色定位，补入知识库。

### 阻塞 C：回复阶段两套“四步流程”未统一

《回复阶段的处理流程》和《顾问的事件信息管理》描述了抽象层和输出不同的两套四步流程，知识库未说明二者如何组合。

**影响**：回复 task 的执行顺序、事件更新责任、信息处理输出和对应 eval 条目。

**建议补全方**：项目人员确认目标业务流程；后端 Agent核查当前实际执行结构，二者一同回写知识库。

### 阻塞 D：外部行为评测的执行材料未完整观察到

当前 evals 定义了 rubric、judge prompt、路径覆盖和指标，但本次可见范围中未发现完整黄金集、实际运行结果、统一通过阈值或评测环境说明。

**影响**：可以生成 eval 定义和交接包，但不能声称行为验证通过。

**建议补全方**：专门评测环境或后端 Agent 返回测试集位置、执行方式、版本和结果。

## 六、非关键疑点

### 卡片数量 26 与 25 不一致

背景说明称 26 张卡，当前搜索索引为 25 张。它应被提示和核实，但如果缺失卡与本次目标提示词无关，不阻塞全部提示词生产。

### 未链接的“产品实现约定”

部分卡片把它列为来源但未链接到内部卡。知识库内容默认真实，因此不自动阻塞；如果某条关键运行规则只依赖这个未定位来源，才升级为知识补全项。

## 七、阶段 3：知识补全分支

新 Skill 在此阶段不会生成上述受影响的 prompts，而会给前台人员拆出至少三份独立补全请求：

1. 门禁 verdict 与工具调用契约；
2. 正式角色定位；
3. 回复阶段两套流程的统一关系。

评测执行材料可以作为第四份请求，但它不阻塞 prompt/eval 的静态生产，只阻塞“行为验证通过”和最终验证状态。

每份补全结果进入知识库后，Skill 回到阶段 2 重新检索，不直接修改提示词。

## 八、阶段 4：架构设计验证

在上述知识补齐的前提下，现有体系证明我们的架构方法可用：

- MainAgent 承担共有底座；
- 三个门禁任务并行、职责相互独立；
- 各门禁 reminder 在内部循环重新注入关键判定轴和工具动作；
- 回复 task 承担事件处理和回复路径；
- anchor 在每次执行重申信息确定性和服务范围。

### 仍需静态核验的点

- 回复 task 重复用户输入标签规则，而 MainAgent 已包含同样规则；需确认 task 是否始终继承 MainAgent，再判断是否为无效重复。
- reminder 与主 prompt 的重复有明确重新注入时机，属于有目的的重复。
- 第三门禁引用七要素时，提示词内列出了七项，避免只引用知识库中模型运行时不可见的定义。

## 九、阶段 5：逐单元生成与 eval 同步

当前项目已有产物展示了可行顺序：

1. `main_agent/system_prompt` + rubric；
2. 三个门禁的主 prompt + reminder + 对应 rubric；
3. 回复 task + anchor + task rubric/judge + anchor rubric。

### 映射特点

- 门禁 reminder 没有各自独立 eval 文件，主要规则在门禁主 rubric 中整体评价；这可以成立，因为“主 + reminder”被视为一个提示词单元。
- task 的确定性检查与 judge 分文件，符合双轨评测。
- anchor 使用 10+ 轮漂移测试，评测目标与其运行时职责对应。

## 十、阶段 6：静态集成与外部交接

### Skill 可完成

- 检查 9 个 prompt 的加载说明、来源卡和配对关系；
- 检查 prompts 与 evals 的对应；
- 生成真实上下文拼装和外部测试要求；
- 输出“待外部评测”状态。

### Skill 不能自行完成

- 三个门禁的真实工具调用和 verdict 消费验证；
- 回复 task 的事件更新与状态机运行验证；
- anchor 的长对话漂移验证；
- 黄金集指标和模型版本稳定性验证。

这些需要后端 Agent 或专门评测环境执行并返回结果。

## 十一、阶段 7：交付状态

在当前可观察信息下，新的 Skill 不应直接给出“最终交付就绪”。合理状态是：

- 如果阻塞 A/B/C 未补全：**设计未就绪**；
- A/B/C 补全，prompts/evals 静态通过但未运行：**待外部评测**；
- 收到可追溯结果并满足阈值：**外部评测通过**；
- 需求清单、静态检查、行为结果和来源同步全部完成：**最终交付就绪**。

## 十二、走查结论

该案例证明分阶段 Skill 可以：

- 从话题和卡片快速重建多层提示词体系；
- 按任务范围获取最小充分知识，而非加载所有业务内容；
- 发现会改变提示词行为的知识冲突并停止生成；
- 区分关键阻塞与非关键疑点；
- 判断规则应进入 system、task、reminder/anchor 还是运行时上下文；
- 同步生成 prompts 与 evals；
- 把真实行为执行交给外部环境，并保持可恢复状态。

当前没有发现需要推翻八阶段工作流的断点。主要改进是：在 Skill 成品中必须把“关键知识冲突阻塞生成”和“静态通过不等于行为通过”写得足够明确。
