# 暂存任务：Prompt 检验范围与问题归因

> 日期：2026-08-11  
> 类型：初版审验期间发现的暂存设计任务  
> 状态：待讨论，尚未修改正式 Skill  
> 主线回归点：用户使用 Claude 对现有 prompts 进行初版审验。

## 一、用户提出的问题

当 Skill 执行“检验已有 prompts”时，不能默认只检查已经生成的每份 prompt 写得好不好，还需要判断：

1. 当前提示词生产范围是否正确；
2. 系统是否确实需要现有这些 prompts；
3. 是否缺少本应存在的 prompt；
4. 是否存在不必要、错误拆分或职责重叠的 prompt；
5. 使用原始六项检查时，是否必须回到知识库逐项对比；
6. 发现错误或疏漏时，如何判断问题属于知识本身，还是 prompt 生成过程。

## 二、待验证的审验层次

后续需要判断 inspection 模式是否明确包含三层，而不是只有内容审校：

### A. 生产范围与 prompt 清单审验

- 目标系统、执行单元和模型调用是否被正确还原；
- prompt 清单是否完整；
- 每份 prompt 是否确有独立存在理由；
- 是否应新增、合并、拆分或删除；
- 职责、加载时机和信息可见范围是否正确。

### B. 单份 prompt 与系统组合质量审验

- 原始六项门禁是否满足；
- 逐字内容、上下文引用、工具、输出和 eval 是否正确；
- 组合加载后是否冲突、重复、遗漏或越权。

### C. 知识库对照与问题归因

检验不能只以现有 prompts 互相对照，应回到知识库和运行时事实。发现问题后至少区分：

- 需求缺失或范围未确认；
- 知识库缺失、冲突、错误、过期或非最终；
- prompt 架构/清单推导错误；
- prompt 生成时误读、遗漏或擅自新增；
- 运行时、工具、schema 或代码契约不一致；
- eval 缺失、错误或已与 prompt 漂移；
- 暂时证据不足，无法归因。

## 三、关键原则候选

- “知识库没有”不自动等于 prompt 生成遗漏，可能是知识疏漏；
- “知识库有但 prompt 没有”也不自动等于错误，需要判断该知识是否适用于当前执行单元、是否应进入动态上下文/code/schema/eval，而非静态 prompt；
- 只有先验证目标范围、prompt 清单和知识来源，才能评价逐字 prompt 是否合格；
- 审验报告应分别给出问题现象、证据、归因、影响范围、置信度和回退阶段；证据不足时不得强行归因。

## 四、后续待办

1. 对照正式 Skill 当前 inspection 流程，确认哪些已有、哪些缺失；
2. 决定是否把“范围/清单审验”设为 inspection 的固定前置阶段；
3. 设计知识库对照的最小必要范围，避免局部检查被扩张为全系统审计；
4. 形成错误与疏漏归因表及报告模板；
5. 用资金安全顾问现有 prompts 的实际审验结果验证分类；
6. 确认后再修改正式 Skill 并重跑结构与场景测试。
