# 系统 Agent 提示词生产 Skill：输入获取模型 V0

> 上游依据：原始输入要求 Skill 不仅知道需要什么，还要解决如何获取、核验和处理缺失信息。  
> 当前状态：共同拆解稿，不是最终 Skill 文案。

## 一、核心原则

Skill 不能默认用户会一次性提供完整资料，也不能用一份通用问卷替代取证。

在本类项目知识库中，已经入库的内容默认真实可用。Skill 不做无差别外部复核；只在发现明显错误、内部冲突、断裂引用、版本异常或显式不确定标记时提出校验。

正确方式是：

1. 先从原始需求中明确生产目标与范围，并识别任务入口模式；
2. 需求已有提示词清单则提取；没有则准备从知识库推导；
3. 通过知识库话题优先定位相关卡组，再读取用户已提供材料与关联卡片；
4. 按需要证明的事实类型寻找最合适的来源；
5. 把已确认、冲突、推断和未知分开记录；
6. 只针对影响生产的缺口继续查找或向用户提问；
7. 通过输入就绪检查后再进入提示词结构设计与编写。

本 Skill 的主要运行场所确定为项目知识库。开始任务时先确认本次生产需要的知识是否已在知识库中，以及知识库当前提供的检索、索引和引用能力。

## 二、需求先行：目标先明确，清单可由 Skill 推导

项目通常带着某种需求启动提示词生产，但人员不一定知道需要哪些提示词。Skill 首先读取原始需求及其在知识库中的任务记录，提取：

- 本次为什么要生产或修改提示词；
- 需求是否已经明确提示词清单及其职责；
- 是新建、重写还是局部更新；
- 已指定的名称、文件、配对关系和加载时机；
- 明确不属于本次范围的提示词；
- 需求给出的交付物与验收要求；
- 原始需求中没有说明、但后续生产必须知道的缺口。

如果需求已有清单，内容分三层记录：

1. **需求明确指定**：直接保留，不重新发明；
2. **从知识库已有体系确认**：例如现有提示词文件、配对和职责；
3. **Skill 分析建议**：需求与知识库都未明确、但基于执行架构认为可能需要的提示词或职责调整。

第三层不能静默写成需求。它需要说明依据，并在影响交付范围时交由前台人员确认。

如果需求没有清单，Skill 进入目标驱动发现模式，通过知识库还原执行单元、上下文、规则作用域和工具边界，形成建议清单。清单确认前不开始逐字编写，但不因人员最初不知道清单而停在需求阶段。

## 三、五类信息如何获取

| 信息类别 | 优先寻找的来源 | 获取时重点核对 |
|---|---|---|
| 目标与交付契约 | 用户原始任务、上游 Issue/PRD、验收要求、已有产物 | 写什么、为何写、范围、受众、格式、完成标准；区分原始要求与后续推断 |
| 运行时事实 | 编排代码、运行配置、工具 schema、接口契约、消息组装逻辑、实际调用日志，其次是架构文档 | 触发时机、真实可见消息、工具参数与返回值、输出消费者、异常路径；文档描述是否与实现一致 |
| 系统关系与继承边界 | 系统架构图、工作流定义、提示词装配代码、父级/底座 prompt、上下游接口文档 | 哪些规则真实继承，哪些信息只属于其他层；引用的概念在当前上下文中是否实际存在 |
| 业务语义与关键约束 | 已批准的产品文档、业务规则、领域知识库、角色与表达规范、合规与安全政策、业务负责人确认 | 事实、方案约定、示例和个人判断是否混在一起；是否存在旧版本或跨项目资料 |
| 证据与验收依据 | evals、测试集、rubric、线上/回归案例、错误记录、提示词评审标准、用户给出的验收口径 | 硬规则与软评分是否分开；规则是否可验证；提示词变化是否有对应测试 |

## 四、来源没有统一的绝对优先级

“代码永远高于文档”或“知识库永远是唯一真相”都不可靠。来源权威性取决于要证明的事实：

- 证明模型运行时实际收到什么：消息组装代码、配置或调用记录通常比产品说明更直接。
- 证明产品应该遵守什么业务规则：已批准的产品或政策文件通常比当前代码实现更权威。
- 证明工具实际接受什么参数：当前工具 schema 或接口契约通常比提示词里的描述更直接。
- 证明表达是否符合角色：正式角色与表达规范比工程实现更适合做判断依据。

当“当前实现”和“目标规则”不一致时，Skill 不应自动选边，而要把它记录成需要解决的冲突。

## 五、证据台账

每项会进入提示词的重要信息至少记录：

- 信息内容；
- 信息类别；
- 来源及位置；
- 状态：已确认 / 方案约定 / 推断 / 未知；
- 时效或版本；
- 适用范围；
- 是否存在冲突；
- 对当前提示词的影响。

这样，“校验可疑知识错误”才会成为生产动作，而不是完成后的泛泛提醒。

## 六、缺口处理顺序

1. **先在已提供材料中查找**：避免让用户重复回答已有内容。
2. **再检查当前可访问的直接来源**：例如代码、配置、schema、知识库、测试和日志。
3. **再请求用户提供明确的缺失资料**：说明需要什么、为何需要、可从何处取得。用户可将请求转交给项目知识库 AI 或相关负责人。
4. **最后才询问业务判断**：只有来源中没有答案，且该问题需要负责人决策时，才让用户作判断。

提问时一次只处理一个会改变提示词结构、行为或验收结果的关键缺口。

## 七、知识库优先的运行环境

项目知识库同时承担：

- 提示词生产任务与交付要求的记录；
- 系统、业务、角色、工具、上下文、前后端实现和评测知识的汇集；
- Skill 生成项目系统提示词时的主要输入；
- 项目知识缺口的登记与补全入口。

理想状态下，无论是提示词任务还是生成提示词所需的系统知识，都应能从项目知识库中取得并追溯。Skill 不应把跨系统临时问答变成常态依赖，而应推动缺失知识回流到知识库。

### 知识库当前可直接提供的内容

可能包括：

- 产品定义、业务规则、角色定位；
- 术语与领域知识；
- 设计决定、历史背景和评测方法；
- 系统架构、前后端契约和提示词任务；
- 经项目人员或代码侧 Agent 取证后回写的实现事实。

### 知识发现顺序

1. 从任务关键词匹配话题，取得主题全景和相关卡组；
2. 读取话题中的综合卡、根卡及其原子卡；
3. 沿引用和反向引用补足上下游知识；
4. 使用全量搜索索引查找话题未覆盖的术语、工具、消息、约束和评测内容；
5. 按五类输入检查覆盖情况，发现真正缺口后再发起补全。

### 外部来源是知识补全途径

企业后端仓库、前端仓库及项目人员不是与知识库平行的日常生产入口，而是知识库出现疏漏时的补全来源：

- 后端 Agent：核查编排、消息装配、工具 schema、接口、配置、prompts、evals、测试和日志等事实；
- 前端 Agent：核查用户输入、前端状态、页面流程、接口调用、展示限制等与提示词任务有关的事实；
- 项目人员：补充业务目标、决策、角色边界、政策、验收口径，以及代码无法回答的项目判断。

### 前台人员的协调职责

Skill 将知识缺口传递给前台人员。前台人员根据缺口性质选择：

- 由项目人员手动补充；
- 转交后端 Agent 取证；
- 转交前端 Agent 取证；
- 从其他明确来源获取。

返回信息应带来源、版本和适用范围，并补充进项目知识库。Skill 随后重新检索知识库并执行输入就绪检查。

### 环境预检需要输出

- 本次提示词任务在知识库中的来源位置；
- 五类输入分别能够从哪些知识条目取得；
- 已发现的知识缺口、冲突或过期风险；
- 建议由哪类人员或 Agent 补充，以及理由；
- 补充内容回写知识库时需要保留的来源信息。

## 八、外部实现证据的作用

后端和前端实现证据仍然重要，但它们通过知识补全流程进入知识库：

- 实现证据回答“系统实际上怎样运行”；
- 业务知识回答“系统应该遵守什么”；
- 两者不一致时，以冲突形式进入知识库，等待项目判断，不能自行覆盖。

## 九、输入就绪检查

进入提示词编写前，Skill 需要判断：

- 提示词生产任务清单是否完整，需求明确要求的提示词与职责是否已保留；
- 目标提示词及其交付范围是否明确；
- 目标执行单元的运行时事实是否足以避免虚构工具、消息或状态；
- 必要上下游和继承关系是否明确；
- 角色、业务规则、行为边界和关键任务约束是否有来源；
- 提示词中将使用的领域概念是否有定义且在执行时可见；
- 重要来源冲突是否已解决或被明确保留；
- 是否知道如何验证生成结果。

任何会影响运行事实、工具契约、核心业务规则、安全边界、职责边界或验收成立的关键资料缺失时，输入就绪检查不通过。

不通过时：

- 不生成提示词，也不生成可能被误用为成品的提示词骨架；
- 输出缺失内容、影响范围、已尝试来源和建议获取途径；
- 获取材料后回到输入就绪检查。

只有非关键资料缺失，且不影响提示词核心行为与验收时，才允许在明确记录缺口的情况下继续。

## 十、资金安全顾问案例校验

以编写第二门禁 `gate/fund_safety` 为例：

- 目标与交付契约：生产资金安全问题判定的主 prompt，还是同时包含 reminder 与评测材料，需要先明确。
- 运行时事实：需核实调用时收到的对话上下文、专属工具 `report_out_of_scope` 的真实契约、verdict 如何被程序消费。
- 系统关系与继承边界：需知道它叠加的 MainAgent 规则和前置三层并行机制；无需加载回复阶段四条路径的全部话术策略。
- 业务语义与关键约束：需取得“资金安全问题”的定义、模糊偏向放行规则、算与不算的边界案例。
- 证据与验收依据：需有明确属于、不属于和模糊边界的测试案例，并验证工具调用与判定取向。

该案例表明：局部任务不需要理解整个系统的全部细节，但五类输入仍然都存在，只是每类的取证范围随交付目标缩小。

## 十一、已确认判断

- Skill 运行环境会改变其主动取证能力，必须在任务开始时预检。
- 在知识库环境中，Skill 应主动检索已有资料；缺失时说明缺口，并提供通过其他来源获取的办法。
- 关键资料缺失时一定不能继续生成提示词。
- Skill 的主运行环境是项目知识库。
- 知识库缺失的后端实现事实，由用户把 Skill 生成的问题转交给后端仓库 Agent，再把可追溯答案带回。
- 后端 Agent 的回答需要核验，不能因其能够读取代码就自动视为无误事实。
- 知识库是 Skill 的主要运行场所和生产输入中心；外部人员与 Agent 是发现疏漏后的知识补全途径。
- 外部取得的关键信息应带来源回流知识库，再由 Skill 重新检索和检查，不以临时对话答案替代项目知识沉淀。
- 提示词生产以项目需求为起点；先提取“要写哪些提示词、各自承担什么职责”，再围绕清单检索知识和设计架构。

## 十二、尚待确认的环境事实

- 项目知识库具体提供哪些检索工具、索引能力和可引用来源格式，后续在编写 Skill 时根据实际环境适配。
