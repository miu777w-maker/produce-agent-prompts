## 3. 问题（按严重度排序）

### 🟠 P1｜检验模式是生产模式的"二等公民"，阶段/确认点/补全分支都对不齐
- **观察**：8 阶段、3 确认点、phase6（逐单元生成）、阶段4（知识补全="停止生成"）——**全部为生产设计**。检验模式下我被迫即兴：跳过 phase6、把 phase5 的"设计"改成"验证"、把"5 维检查"自行映射到"6 门禁 + 静态 8 项"、把阶段4的"停止生成"改成"把冲突记为发现"。
- **证据**：SKILL.md「按八阶段推进」「只保留三个人工确认点」；`workflow-and-state.md` 阶段4/6/7；本文件 §1 的偏差列。
- **影响**：执行者必须自行把检验流程"反推"出来，不同执行者会推出不同流程，一致性不可控；也使检验模式看起来像"生产的简化版"而非一等流程。
- **建议改法**（改 `SKILL.md` + `workflow-and-state.md`）：
  1. 在 SKILL.md「选择入口模式」第 3 条（检验）下，加一个**检验子协议**：明确 ① 适用阶段（1/2/3/5验证/7静态/8，跳过6）；② "知识/职责/上下文/运行时/静态"5 维检查如何映射到 6 门禁 + 静态 8 项；③ 检验的交付物形态（一份检验报告，含：来源映射、6 门禁验收结论、静态 8 项、按严重度排序的发现、状态、后续入口）；④ 检验可赋的状态范围（通常 `design-not-ready`..`awaiting-external-evaluation`，不产生 `final-ready`）。
  2. 把阶段4 的"停止生成"改写为模式相关：**生产**模式下停止生成并出补全请求；**检验**模式下把冲突/缺口记为"发现"继续，不阻塞报告产出（除非用户要的是"修复"）。
  3. 为检验定义自己的确认点（通常 1 个：确认范围与"只报告不修改"），而非沿用生产的 3 个。

### 🟠 P2｜验证脚本与检验/草稿场景错配
- **观察**：SKILL.md 反复要求"运行 `scripts/validate_prompt_package.py` 只证明确定性结构状态"。但脚本硬依赖 `prompt-package.json` manifest + 8 项产物（`runtime_environment`/`execution_context`/`business_role`/`responsibility_visibility`/`attention_plan`/`knowledge_conflicts`/`runtime_contract`/`source_mapping`）+ 每个 unit 的 `{prompt, eval, version, eval_version, tools, sources}`。在**检验已有草稿**时，这些几乎必然不存在 → 脚本直接报"Manifest does not exist"，是死路。skill 没承认这一点；我是自己把"无 manifest"当成一条确定性**发现**处理的，并非 skill 所教。
- **证据**：`scripts/validate_prompt_package.py` `REQUIRED_ARTIFACTS`、`validate()`；SKILL.md「生成和校验规则」。transcript 中我搜 manifest 后判定"无法运行"。
- **影响**：执行者在检验/草稿场景下，要么困惑"为什么脚本跑不了"，要么误判"确定性校验通过/失败"。脚本的强 manifest 假设实际上是**生产产物**的校验器，不是通用校验器。
- **建议改法**（改 SKILL.md「生成和校验规则」+ 可选改脚本）：
  1. SKILL.md 显式声明："该脚本仅校验**已产出 manifest** 的包；检验已有草稿时若无 manifest，**'无 manifest'本身即一条确定性发现**（产物未结构化、追溯链不成立），而不是脚本失败。"
  2. （可选）脚本增加一个"轻量检验模式"参数，仅做 prompt/eval 配对、来源标注、占位符等不依赖 manifest 的检查；或输出更明确的"manifest 缺失 ≠ 校验失败"提示。

### 🟠 P3｜缺"派生综述文档"处理指引（本次实际踩坑）
- **观察**：项目里有一份 `项目背景说明.md`，文件头明写"作为'规范提示词生产过程'这一 Skill 的背景输入"。skill 只说"优先使用项目知识库；把入库知识视为项目事实"，但**一份预处理好的综述文档看起来也像"项目知识库"**。我默认拿它当检索地图与事实来源，结果用户纠正"那是一份无用文件，不要读"，我才改读 `Zettel_KDB/` 卡片原文。
- **证据**：SKILL.md「保持边界」；transcript 中用户消息"不要读取背景文档说明，那是一份无用文件"。
- **影响**：当项目同时存在"原始 KB"和"二次综述/摘要"时，skill 无法引导执行者优先核对两者权威性，可能导致整条检索建立在不可靠的综述上（本次靠用户纠偏才挽回）。这是最典型的"看起来无害、实际偏航"的坑。
- **建议改法**（改 SKILL.md「保持边界」或新增"知识源分级"小节）：
  1. 增加规则："区分**原始知识源**（卡片/记录/代码/schema）与**派生综述**（摘要/背景说明/Q&A 综述）。**事实断言一律追溯到原始源**；派生综述只能当导航线索，不可当事实来源。"
  2. 在阶段2 或阶段3 加一个启动问句："项目里是否存在预处理好的综述/背景文档？若有，请确认哪些文件是权威事实源、综述是否可作为导航。"——把本次的用户纠偏前置成标准问诊。

### 🟡 P4｜"按需读取资源"无硬保证 → 半数 reference 在合法执行中未被加载
- **观察**：SKILL.md「按需读取资源」把 6 个 reference 设计成"用到才读"。本次**整套系统检验**是合法、完整的任务，却只触发了 3 个 reference，`knowledge-discovery-and-gaps.md`/`prompt-architecture-and-runtime.md`/`artifact-templates.md` 全程没读。原因：项目结构清晰 + 我用了综述文档（P3），就没去翻这些 reference。
- **证据**：SKILL.md「按需读取资源」；transcript 中我只 Read 了 3 个 reference。
- **影响**：如果这 3 个未读 reference 里含**必须遵守的硬规则**（例如知识发现的强制步骤、artifact 的必填字段），skill 无法保证执行者遵守——"按需"退化为"可能跳过"。这也意味着**本反馈对那 3 个 reference 无结论**（诚实边界）。
- **建议改法**（改 SKILL.md 结构）：
  1. 把每个 reference 中"**不可绕过的少量硬规则**"内联进 SKILL.md（一两行），reference 只保留展开细节与模板。这样即便 reference 未读，核心规则也在主指令里。
  2. 或在对应阶段加显式 checkpoint："进入阶段3 前，确认已读 `knowledge-discovery-and-gaps.md` 的'检索协议'节"。

### 🟢 P5｜"入口模式"术语重名，且知识入口模式在检验下不适用却未说明
- **观察**：SKILL.md 里"**选择入口模式**"指任务入口（生产/evals/检验），紧接着"**识别知识入口模式**"指知识入口（明确清单/目标驱动/变化驱动）。两者都用"入口模式"，措辞极近，需细读才能分。而且"知识入口模式"是"推导 prompt 清单"的前置，**检验模式下根本不推导清单**（只核验已有），这三个知识模式都不适用——skill 没说明。
- **证据**：SKILL.md「选择入口模式」与「再识别知识入口模式」两段。
- **影响**：认知负担 + 执行者可能在检验模式下硬套"知识入口模式"而徒增困惑。
- **建议改法**：把"知识入口模式"重命名为"清单推导模式"（与"任务入口模式"区分）；并注明"检验模式不推导清单，跳过本步"。
